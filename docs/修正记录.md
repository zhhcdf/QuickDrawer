## C4. 便签独立编辑器（2026-11-08）

### 现象

便签卡片的正文区域被 `NoteBodyMaxHeight=150` 限高，写长一点的笔记就成了在一条窄缝里滚动；
而且卡片正文只有 12px 字号、没有撤销/重做，写长文本体验很差。

用户需求（原文）："我想给便签卡片增加一个双击区域（或者单击按钮）打开一个独立编辑器进行文字编辑，
关闭自动保存为便签的功能。独立编辑器具有类似记事本上的简单文字工具（如加粗、斜体、删除线、链接等）"。

经澄清后定为：**纯文本编辑器，不做富文本**；入口两个（双击正文 + 标题栏 ✎ 按钮）；
关闭即自动写回卡片；卡片本身仍保留就地编辑。

### 根因

不是缺陷，是缺失的功能。但实现时有三个真实的坑，每一个都会让功能"编译通过、一用就崩"或"用着用着丢数据"：

**坑 1：`StaticResource IconButton` 跨窗口引用，编译期不报错、运行期抛异常**

`src/QuickDrawer/DrawerWindow.xaml:38` 的 `<Style x:Key="IconButton" TargetType="Button">`
写在 DrawerWindow 的 `<Window.Resources>` 里 —— 这是**窗口级局部资源**，别的窗口的查找链里根本没有它。
而新建的 `src/QuickDrawer/NoteEditorWindow.xaml` 三个工具按钮都写了
`Style="{StaticResource IconButton}"`。

`StaticResource` 是**运行时**解析的：XAML 编译器不检查它能否找到，`dotnet build` 0 错误 0 警告，
一打开编辑器就 `XamlParseException: Cannot find resource named 'IconButton'`。

印证这一点的旁证：`src/QuickDrawer/SettingsWindow.xaml` 和 `src/QuickDrawer/PromptEditorDialog.xaml`
里 grep 不到任何 `StaticResource` —— 项目里其他窗口一直只用 `DynamicResource` 引主题键
（定义在 `src/QuickDrawer/Themes/Dark.xaml` / `Light.xaml`，由 `ThemeService.Apply(bool dark)`
运行时插进 `Application.Current.Resources.MergedDictionaries`）。

**坑 2：`ShutdownMode="OnExplicitShutdown"` 下，漏关的编辑器窗口会让进程退不出去**

`src/QuickDrawer/App.xaml` 设的是 `ShutdownMode="OnExplicitShutdown"`（托盘应用的常规做法：
关掉某个窗口不代表退出程序）。代价是：任何没被显式 `Close()` 的窗口都会留着，
`Application.Shutdown()` 之前不清理干净，进程就卡住不退出。

**坑 3：`Window.Owner` 会把编辑器绑死在面板上**

第一版照着 `PromptEditorDialog` 的写法想设 `Owner`。但 `Owner` 的语义是"从属"：
所有者窗口隐藏/最小化时，从属窗口跟着走。面板一收起，编辑器就跟着消失，
用户正在编辑的内容看起来"没了"（其实还在，但体验上等于丢失）。

### 验证方法

**编译期查不出坑 1，所以门禁探针必须真的把窗口构造出来。**
`probe/_verify_note_editor.ps1`（18 项）：

1. 反射加载 exe，断言 `NoteEditorWindow` / `NoteCardViewModel` / `NoteItem` 类型、
   `DrawerWindow.OpenNoteEditor` / `DrawerWindow.NoteEdit_Click` 方法存在。
2. `[System.Windows.Application]::Current` 为空时 new 一个，然后**手动加载主题字典**。
   注意路径必须带程序集名：`pack://application:,,,/QuickDrawer;component/Themes/Light.xaml`。
   照抄 `ThemeService` 里那个不带程序集名的 `pack://application:,,,/Themes/Light.xaml` 会失败 ——
   无程序集名时解析到**入口程序集**（这里就是 PowerShell），找不到资源。
3. 造 `NoteItem` + `NoteCardViewModel`，反射拿 ctor `(NoteCardViewModel, Window)` 调 invoke。
   **这一步就是抓 `XamlParseException` 的关键检查**；失败时把 InnerException 链一路拨到底，
   打印异常类型名 + 消息，否则只能看到一个无信息量的 `Exception calling ".ctor"`。
4. 断言 `window.Resources.Contains('EditorToolButton')` —— 证明编辑器用的是自己的本地样式，
   而不是又去引别人的键。
5. 断言 `NoteBox` / `StatText` 字段解析成功、编辑器载入了卡片正文。
6. 注入 `NotesSaveRequested = [Action]{ $script:saveCount++ }`（PowerShell 里 scriptblock 转 `[Action]`
   就得到委托）。
7. **必须真的 `Show()`**：不显示就 `Close()`，部分 WPF 版本不触发 `Closed` / `OnClosed`。
   窗口摆到 `Left/Top = -4000`、`ShowInTaskbar = $false`，离屏跑，不干扰用户。
8. 改 `NoteBox.Text` 后要把 Dispatcher 队列跑到 `Background` 优先级之外，
   统计才是新的值（`UpdateStat` 是延后一拍算的）。
9. 反射调 `InsertTime_Click`，断言正文里出现 `\d{4}-\d{2}-\d{2} \d{2}:\d{2}`。
10. 反射调 `Done_Click` → Close → OnClosed → SaveToCard，断言 `saveCount == 1` 且卡片正文已更新。
11. 再调一次 `SaveToCard`，断言 `saveCount` 仍是 1（`_saved` 防止重入）。

**实测**：18 项全 PASS，`RESULT: PASS (18 checks)`。关键行：

```
PASS  window constructed (XAML resources resolve)
PASS  window defines EditorToolButton locally
PASS  stat text updated  stat='10 字 · 2 行'
PASS  insert time stamps at caret  tail='行\r\n2026-11-08 19:06 '
PASS  save callback fired once  count=1
PASS  no double save  count=1
```

脚本**必须存成 UTF-8 with BOM**（含中文，Windows PowerShell 5.1 无 BOM 时按 ANSI 解码，
会报一堆指向无关行号的假解析错，如 `Unexpected token 'check' in expression or statement`）。

### 修复

**新增文件**

### 防复发

1. **XAML 里 `StaticResource` 找不到不会在编译期报错**。新窗口要复用的样式，要么在
   `Application.Resources` / 主题字典里（用 `DynamicResource` 引），要么在自己的
   `<Window.Resources>` 里重新定义。验证只能靠"真的把窗口构造出来"的探针。
2. `ShutdownMode="OnExplicitShutdown"` 的项目里，**每新建一个窗口都要在 `Window_Closing` 里登记清理**。
   漏一个，进程就退不出去 —— 而且表现为"点退出没反应"，很难联想到是某个没人注意的窗口。
3. `Window.Owner` 不是"跟谁有关系"，而是"从属于谁"：所有者隐藏/最小化，从属窗口跟着走。
   只是想让窗口盖在上面，应该用 `Topmost`（临时）或 `Activate()`，不要设 Owner。
4. 富文本改造的成本容易被低估：`notes.json` 是纯文本 schema，改 RTF/HTML 要连带改存储格式、
   搜索、预览、卡片渲染四处，还会引入旧数据迁移。用户真实痛点（正文限高 150px、不能撤销）
   用纯文本编辑器就能解决 —— **先解决痛点，再谈格式**。
5. 探针脚本写中文就必须存成 UTF-8 with BOM，这是本项目第 9 条踩坑，别再重踩。

### 影响面

只新增一个窗口与两个入口，不改便签的存储格式（`notes.json` 仍是 v2 纯文本），
不改卡片渲染、搜索、预览。升级前后数据完全兼容，不需要迁移。


## 工具与环境踩坑（不要重踩）

### 1. `edit` 工具改不了含反斜杠的 C# 字符串
`old_string` 里的 `\\` 经过 JSON 解码会塌掉一层，永远匹配不上。
**改用**：写 Python 脚本文件（`write` 写 `.py`），脚本里用普通字符串（不做转义折叠），
`ops_bash` 跑 `python probe/_xxx.py`，脚本内先 `assert src.count(anchor) == 1` 再替换。
这个方法一次就能成功。

### 2. 读文件工具把 `\0` 显示成 `\\0`
我据此误判 `Encoding.Unicode.GetBytes(f + "\0")` 是 bug（以为写的是反斜杠+字符0），
实际源码是对的。**判断转义层数必须以 `python -c "print(repr(line))"` 的原始字节为准。**

### 3. Python 脚本里不要用中文做锚点
全角/半角、空格差异会导致匹配失败。锚点只用 ASCII。

### 4. `APPDATA` 环境变量不能隔离测试数据
`ConfigStore.BaseDir`（`App.xaml.cs`）用
`Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData)`，
Windows 上走 `SHGetFolderPath`，**不读 `APPDATA` 环境变量**。
我曾因此在 B7 测试时把用户真实的 34 条剪贴板历史覆盖成 2 条测试数据，
已用 `.bak-b7` 还原并 `md5sum` 核对一致（`68e866345a1da8747058727999857a6`）。
**碰用户数据前必须先备份。**

### 5. Python 脚本删区间时要检查闭合括号
B8 的脚本把 `ClipboardConfig` 的类闭合 `}` 一起删了，报 `error CS1513: 应输入 }`。

### 6. `ops_grep` 的限制
- `afterContext` 上限 32 行。
- 对 `src/QuickDrawer` 整体扫描时 `skippedFiles` 会很大（bin/obj 二进制），
  要精确结论就扫单个文件。

### 7. Pillow 的 ICO 写出器有 bug
同时传 `sizes=` 和 `append_images=` 只写第一帧（实测 9 帧只落 1 帧）。
必须手工拼 ICO 容器：6 字节头 + 每帧 16 字节目录项 + PNG 载荷，256 的宽高字节写 0。

### 8. `Dispatcher` 类型名在 `App.xaml.cs` 里不可见
`App.xaml.cs` 的 using 里没有 `System.Windows.Threading`。
`Application.Dispatcher` 是属性，但需要类型名时必须写全名。

### 9. `edit` 工具会把文件的 BOM 抖掉

`probe/*.ps1` 里不少脚本是 UTF-8 with BOM。用 `edit` 改完后 BOM 就没了，
Windows PowerShell 5.1 按 ANSI 解码中文，报一堆与实际错误无关的解析错：

```
Unexpected token '}' in expression or statement.
The string is missing the terminator: '.
```

**每次 `edit` 改完脚本都要补回 BOM**：

```powershell
$t = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
[System.IO.File]::WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($true))
```

验证的方法是**直接跑 Parser**，而不是看报错行号（行号是错的）：

```powershell
$e = $null
[void][System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$e)
if ($e.Count) { $e | % { "$($_.Extent.StartLineNumber): $($_.Message)" } } else { 'PARSE OK' }
```

### 10. `git push` 报 `could not read Username`：这台机器没有任何 credential.helper

2026-11-08 推 1.0.3 时实测：`git config --get-all credential.helper` 为空，
`%USERPROFILE%\.git-credentials` 不存在，于是

```
fatal: could not read Username for 'https://github.com': No such file or directory
```

但 `gh auth status` 是登录状态。直接借 gh 的凭据助手即可：

```bash
HTTP_PROXY=http://127.0.0.1:3067 HTTPS_PROXY=http://127.0.0.1:3067   git -c credential.helper="!D:/software/gh/gh.exe auth git-credential" push origin main
```

两个必须的细节：

- **路径用 `/` 不能用 `\`** —— `!` 助手是当 shell 命令跑的，反斜杠会被当转义。
- `origin` 走 https 时 **一定要带代理环境变量**。本机系统代理是
  `127.0.0.1:3067`（`ProxyEnable=1`），但 git 是 Go/curl 系的，不读 WinINET 设置，
  不带就直接 `Recv failure: Connection was reset`。先 `TcpClient.ConnectAsync` 探一下端口在不在监听再注入。

### 11. PowerShell 5.1：原生命令 `2>&1` + `$ErrorActionPreference='Stop'` 会把预期内的错误变成崩溃

`probe/_release.ps1` 里查 Release 是否已存在：

```powershell
& $GhExe api "repos/$Repo/releases/tags/v$Version" 2>&1 | Out-Null
if ($LASTEXITCODE -eq 0) { Die "Release 已存在" }
```

对“还没发布的新版本”这个请求**必然 404**，而 gh 把 `gh: Not Found (HTTP 404)`
写在 stderr，`2>&1` 把它变成 ErrorRecord，配上 `Stop` 直接抛 `NativeCommandError`。
结果就是**每次发布新版本都在这一步挂掉**，而不是继续往下走。

修法：只在这一次探测里把 EAP 临时降到 `Continue`，只看 `$LASTEXITCODE`：

```powershell
$eap = $ErrorActionPreference
$ErrorActionPreference = 'Continue'
try { & $GhExe api "..." 2>&1 | Out-Null } finally { $ErrorActionPreference = $eap }
```

同一个坑也说明：**判断外部命令成功与否只能看退出码**，
不能让 stderr 的内容自己变成异常。

### 12. UIA 里 `AutomationProperties.Name` 落在 `Name`，不是 `AutomationId`

WPF 给控件写 `AutomationProperties.Name="EditCard"`，自动化树里查到的是
**`Name` 属性 = `EditCard`，`AutomationId` 是空字符串**。

写探针时按 `AutomationIdProperty` 去查，永远返回「控件不存在」，
很容易被误读成「界面真的没渲染出来」—— 这次为此白查了一轮 XAML。

判定方法：先用枚举脚本把 `Name` 和 `AutomationId` **两个都打出来**，
再决定按哪个键查：

```powershell
$walker.GetCurrentPropertyValue([System.Windows.Automation.AutomationElement]::NameProperty)
$walker.GetCurrentPropertyValue([System.Windows.Automation.AutomationElement]::AutomationIdProperty)
```

`probe/_dump_ids.ps1` 就是干这个的，留着复用。

**推论**：`AutomationProperties.Name` 和 `AutomationProperties.AutomationId`
是两套独立的东西。想给自动化留稳定标识，用 `AutomationId`；
`Name` 留给读屏软件播报。

---

### 13. `notes.json` 把非 ASCII 存成 `\uXXXX` 转义，直接 `Contains` 恒为 false

`NoteStore.Save` 走 `JsonSerializer`，中文被写成字面量 `\u7AEF\u5230\u7AEF...`。
所以拿原始文件文本 `$json.Contains('端到端测试写入')` 判断「有没有写进去」**永远是 false**，
看起来像功能失效，其实数据早就在文件里了。

`od -c` 一眼能看出来：

```
$ od -c notes.json | head -3
... " T e x t " : " \ u 7 A E F \ u 5 2 3 0 ...
```

修法：**先反序列化再比**，不要对原始 JSON 文本做子串匹配：

```powershell
$obj = Get-Content -LiteralPath $notes -Raw -Encoding UTF8 | ConvertFrom-Json
$has = $false
foreach ($n in $obj.notes) { if ($n.Text -and $n.Text.Contains($marker)) { $has = $true } }
```

同理，**验证写盘一律不要用 `Select-String` / `Contains` 匹配原始文件**，
JSON 的转义、缩进、键序都可能让匹配落空。

### 14. `TextBlock` 用 `AutomationProperties.Name` 会把文本内容盖掉

`StatText` 这种「内容本身就是信息」的文本块，如果写成：

```xml
<TextBlock x:Name="StatText" AutomationProperties.Name="NoteStat"/>
```

UIA 读到的 `Name` 就是字面量 `NoteStat`，**「10 字 · 2 行」被彻底遮住** ——
读屏软件念不出字数，自动化脚本也断言不了。

`TextBlock` 的 UIA `Name` 默认就是它的 `Text`，正确做法是只加 `AutomationId`：

```xml
<TextBlock x:Name="StatText" AutomationProperties.AutomationId="NoteStat"/>
```

**通用规则**：能给元素加 `AutomationId` 的场合就别用 `Name`。
`Name` 是给"人要听的话"用的，覆盖它就等于把真实内容藏起来。

### S1 划词捕获挪出 UI 线程

根因：`SelectionCapture.Capture()` 用 `Thread.Sleep(40)` 轮询，`PollCount=20 × CopyAttempts=2`
= 最长 **1600ms 同步阻塞**，且经 `SelectionWatcher.HandleDrag` 在 UI 线程执行。
Ctrl+C 无效或剪贴板被占时整个托盘程序卡死。

改成 `CaptureAsync()`：起一个 **STA** 后台线程（`System.Windows.Clipboard` 依赖 OLE，
MTA 线程调用会抛 `ThreadStateException`，所以不能用 `Task.Run`），用 `TaskCompletionSource` 回传。
`HandleDrag` 改 `async void`（整体在 try/catch 内，是事件回调，安全），await 后补 `_disposed` 守卫。

### S2 终端黑名单

`SendCtrlC()` 无条件注入 Ctrl+C。在终端里拖选文字 = 发 SIGINT，**打断用户正在跑的命令**。

新增 `IsForegroundTerminal()`：前台窗口进程名查表（conhost / OpenConsole / WindowsTerminal /
wt / cmd / powershell / pwsh / mintty / bash / ConEmu / ConEmu64 / Cmder / alacritty / wezterm-gui / Hyper），
命中就跳过捕获。拿不到进程名按"不是终端"处理（宁可漏判，不要让功能整体失效）。

**故意不放 `Code.exe`（VS Code）**：集成终端里 Ctrl+C 有选区时默认是复制不是中断，
放进去会误伤主要使用场景。

### S3 快照失败不清空剪贴板

两处 `RestoreClipboard` 都是 `saved == null` 时 `Clipboard.Clear()`。
但 `saved == null` 表示"取快照就失败了"（剪贴板被别的进程占着，很常见），
此时剪贴板里是**用户自己的内容**，清空是纯粹的破坏。改为什么都不做。

### S4 导航白名单

**唯一的静默外泄路径**：`NavigationStarting` 只记日志从不 `e.Cancel`，
`NewWindowRequested` 把任意 URI 导航到当前视图，而 `SendPromptAsync` 拿到
`core` 后不校验 host 就 `insertText` + 回车。页面一旦被带到第三方站点，
用户划词选中的文字会被自动键入并发出，全程无提示。

**为什么不能简单在 NavigationStarting 里 cancel**：登录必须跳第三方域名
（open.weixin.qq.com、passport.* 等），一律拦会直接废掉登录。

**采取的方案**：把"能不能导航"和"能不能自动灌文字"分开。
导航照旧放行；`AssistantProviders.IsTrustedHost(url)` 只允许"等于某 provider 的 host 或它的子域"，
`SendPromptAsync` 和 `SendPromptWithImageAsync` 两个入口都先过 `EnsureTrustedPage()`。
用户自己手动在页面里输入不受限 —— 那是他看着屏幕在操作。

### S5 WebView2 初始化可重试

`GetEnvironmentAsync()` 用 `_envTask ??=` 缓存 Task，失败后缓存的是 **faulted Task**，
后续每次 await 抛同一异常，用户装好 Runtime 也救不回来，只能重启。
改为 catch 里把 `_envTask` / `_env` 置回 null 再 rethrow。

### S6 全局异常提示

三个钩子原来都只写日志：
- `DispatcherUnhandledException` **没有 `ex.Handled = true`** → UI 线程任何未捕获异常直接杀进程，
  托盘程序突然消失，用户不知道为什么
- `UnobservedTaskException` **没有 `SetObserved()`**

改为：UI 异常写日志 + `Handled = true` + 弹自动关闭的**非模态**提示窗；
域异常尽力提示一次；Task 异常只 `SetObserved()`（弹窗会变噪音）。
提示 10 秒限流，避免异常风暴刷出几百个窗口。

顺带接上 `CorruptFile.TakeNotices()`：启动后如果归档过损坏文件，明确告诉用户
"已备份到原目录，旧数据没被删除"，而不是静默用默认值。

### S7 托盘 HICON

`CreateIconFromResourceEx` 返回的 HICON 归调用方所有，必须 `DestroyIcon`。
`NIM_DELETE` 只让外壳不再显示，不释放句柄。`Dispose()` 里补上，注意顺序（先 NIM_DELETE 再销毁）。

### S9 单条大小上限

三个问题：
1. `ClipEntry.SizeBytes` 是 `int`，单条超 2 GB 溢出成负数 → 字节账算错 → 再也淘汰不掉任何东西
2. `MaxBytes`（默认 2 GB）管总量管不住单条，一条 500 MB 图片照样先落盘
3. **M6**：单条超总量上限时，淘汰完所有非锁定项后 `idx is null` → `break`，
   调用方照样 `Add` → "淘汰光了别人，自己还是超限"

改法：
- `SizeBytes` 改 `long`（`ClipEntry` + `ClipboardStore.StoredEntry`）
- 新增 `ClipboardConfig.MaxItemBytes`，默认 **32 MB**（文本 = 1600 万字符，图片 ≈ 2800×2800 32 位图）
- `EvictIfNeeded` 返回 `bool`，false 表示"这条本身就不该进"；调用方跳过 Add 并回滚 `_seen`
- 单条上限检查放在去重**之前**，省得把巨型内容的 key 塞进 `_seen`

## net48 迁移实测结论（体积项，2026-11-01）

### 目的
用户原始硬指标是"尽量减小体积"。自包含单文件压缩后仍有 **65.39 MB**，其中 99.6% 是 .NET 运行时、应用代码仅 253 KB。要真正小下来只有一条路：不再自带运行时。

### 三条路线实测对比（同一份源码、同一台机器）

| 路线 | 体积 | 依赖 | 结论 |
|---|---|---|---|
| 自包含单文件（现状） | **65,391,810 B / 65.39 MB** | 无 | 满足"零依赖"，但体积大 |
| 框架依赖单文件 | 1,646,809 B / 1.65 MB | 需装 .NET 10 Desktop Runtime | 违背零依赖 |
| **net48 框架依赖** | **2,762,211 B / 2.63 MB（含 pdb）** | Win10 1903+/Win11 系统自带 | **零依赖 + 体积小，两者兼得** |

## net48 版助手页 BadImageFormatException（2026-11-01 结案）

### 现象
net48 版打开「助手」标签，页面位置显示：

```
助手页不可用：BadImageFormatException: 试图加载格式不正确的程序。
(异常来自 HRESULT:0x8007000B)
```

其余全部功能正常：剪贴板、便签、目录、热键、托盘都没问题。

### 根因
`WebView2Loader.dll` 是 **x86** 原生库，而进程是 **64 位**（AnyCPU 在 x64 系统上跑 64 位）。

- `D:\QuickDrawer-net48\QuickDrawer.exe` = managed **AnyCPU**（不是 x86）
- `D:\QuickDrawer-net48\WebView2Loader.dll` = **native x86**  <- 元凶
- `runtimes\win-x86\native\WebView2Loader.dll` 同样是 x86（说明打包时就选错了目录）

64 位进程加载 32 位原生 DLL 必然 `0x8007000B`。只有助手页挂，因为只有它依赖这个 loader。

**为什么会选错**：net48 变体的 csproj 里只有 `<Platforms>x64</Platforms>`。
`<Platforms>` 只是「本工程可以构建哪些平台」的声明，**不决定编译目标**。
缺 `<PlatformTarget>` 时 net48 产物是 AnyCPU，而 NuGet 挑原生资源时按默认 x86 走，
于是把 `runtimes/win-x86/native/WebView2Loader.dll` 复制到了输出根目录。

### 验证方法（可复现）
1. **判平台必须读 COR20 header 的 Flags，不能读 COFF machine。**
   AnyCPU 程序集的 COFF machine 同样是 `0x14c`(i386)，只看这个字段会得出「exe 是 x86」的错误结论（我一开始就踩了这个坑）。
   正确工具：`probe/_pe_platform.py`，读 `ILONLY=0x1` / `BIT32_REQUIRED=0x2` / `BIT32_PREFERRED=0x10000`。
2. **隔离环境证 WebView2 可用**：建 net48 控制台工程（`PlatformTarget=x64`）调
   `CoreWebView2Environment.GetAvailableBrowserVersionString()`，应返回运行时版本号。
3. **应用内验证**：不起助手的判断标准不能用截图猜，用子进程数——
   `@(Get-Process msedgewebview2).Count` 从 0 变成 6 即说明 WebView2 真的起来了。
   切标签用 UI Automation，不要用鼠标点坐标（见下方教训）。

### 修复
`QuickDrawer.csproj` 在 `<Platforms>x64</Platforms>` 后补两行：

```xml
<PlatformTarget>x64</PlatformTarget>
<Prefer32Bit>false</Prefer32Bit>
```

`PlatformTarget` 同时做两件事：让 NuGet 选 `runtimes/win-x64/native/WebView2Loader.dll`，
并让程序集带上 x64 标记，杜绝在 32 位宿主里被加载。

### 防复发
1. **任何 net48 / 非 SDK 默认平台的构建，都必须显式写 `PlatformTarget`。** `<Platforms>` 不做这件事。
2. **判 .NET 程序集平台只看 COR20 Flags，不看 COFF machine。**
3. **验证 WebView2 是否真的起来，看 `msedgewebview2` 子进程数，不要看截图。**
4. **操作应用内控件用 UI Automation + `AutomationProperties.Name`，不要用手工估的屏幕坐标。**
   本项目 `DrawerWindow.xaml` 已有 `TabNotes`/`TabClipboard`/`TabAssistant` 等 18 个无障碍名。

### 附：本轮踩到的操作陷阱
- **抽屉本来就开着时再按 Win+Alt+N 会把它关掉**，之后的点击全落在桌面上。
  必须先采样 (1700,300) 像素判断开合（面板浅色：`r>215 and g>215 and b>220 and (b-r)<30`）。
- 抽屉打开后 400ms 不把鼠标移回面板区就会被 auto-hide 收起，截图只拍到壁纸。
- `dotnet publish` 目标目录被运行中的进程占用时，报 `MSB3027/MSB3021` 但接了 `| tail` 之后
  bash 的 `$?` 仍是 0，极易误判成功。**必须先 `Stop-Process` 再 publish，并检查输出里有无 `error`。**
- PowerShell 5.1 用 `-File` 跑 UTF-8 无 BOM 且含中文的脚本会乱码或报语法错，改走 Python + `PIL.ImageGrab`。

## 剪贴板富格式与图片捕获修复（2026-11-01 晚）

### 用户可见症状

用户报告（原话）：

> 我发现剪贴板对word表格、excel表格和截图都支持的不好。1. word表格和excel表格无法保持原格式，
> 复用时只能粘贴文字内容，无表格了。2. 使用截图工具截图后剪贴板里看不到截图内容。

### 根因（四条，全部实测确认，不是推断）

**根因 1：优先级把富格式饿死了。**
`TryReadClipboard()` 原本按「文件 > 文本 > HTML > 图片」依次 return。Word / Excel 复制表格时
**同时**放 `CF_UNICODETEXT` + `HTML Format` + `Rich Text Format`，纯文本分支先 return，
HTML/RTF 永远轮不到。这是「表格只剩文字」的直接原因。

**根因 2：`CF_HTML` 格式 id 被硬编码成错误值。**
原代码 `const uint CF_HTML_FORMAT = 0x00000100;`（=256），探测分支写
`else if (format == 0x00000100 || format == 0x000004C8) hasHtml = true;`。
实测 `RegisterClipboardFormatW` 的返回值：

| 格式名 | 第一次实测 | 第二次实测（另一会话） |
| --- | --- | --- |
| `HTML Format` | `49395` (0xC0F3) | `50107` |
| `Rich Text Format` | `49301` (0xC095) | `49945` |
| `PNG` | `49471` (0xC13F) | — |
| `System.Drawing.Bitmap` | `49860` (0xC2C4) | `49860` |

→ 注册格式从 `0xC000` 起、**每个会话动态分配**。硬编码 `0x100` 永远不命中，
`hasHtml` 恒为 `false`。**即使把优先级调对，HTML 分支也进不去。**

**根因 3：图片去重 key 全局碰撞，第一张之后全被静默丢弃。**
`ComputeKey()` 用 `e.Text ?? e.Preview ?? ""` 做内容指纹，而图片条目 `Text` 恒为 `null`、
`Preview` 被 `ReadImage()` 固定写成字符串 `"图片"`。于是 `content` 恒等于 `"图片"`。
实测三种不同大小（256040 / 900000 / 120000 字节）的图算出的 key **完全相同**：
`Image|D24C10D37DB0FEEA7BD73498...`。
第一张图进 `_seen` 之后，每张新图都在 `OnClipboardUpdated` 的
`if (_seen.Contains(key)) return;` 处被丢弃，**而这条分支不打任何日志** ——
这正是「设了图但 `diag.log` delta=0、一条记录都没有」的原因。

**根因 4：`WriteBack` 不支持 Html/Rtf。**
只有 `case ClipKind.Text` / `ClipKind.Files` / `ClipKind.Image`，末尾 `default: return false;`。
即便捕获到富格式，粘回去也必然失败。

## 剪贴板乱码与 Word 自动退出修复（2026-11-02 晚）

### 现象（用户原话）

> 剪贴板模块出问题了，今天测试显示的全是乱码。测试了图片、word表格和excel表格，
> 在测试word文字复制时总是造成word自动退出。

三个独立症状：
1. 历史列表里 Word / Excel 表格条目全部显示为乱码；
2. 复制 Word 文字（划词取词触发）时 Word 进程反复自动退出；
3. 图片条目看起来也"乱"，实际是列表里相邻的 Html 条目在乱，图片本身没坏。

### 根因一：HTML Format 是 UTF-8，却按 UTF-16 解码

`ClipboardService.ReadHtml()` 原来用 `Marshal.PtrToStringUni(p)`。

- `HTML Format` 剪贴板数据是 **UTF-8 字节流**（`Version:0.9\r\n` 头部 + HTML），不是 UTF-16。
- `PtrToStringUni` 按 UTF-16LE 解释，中文每个 3 字节的 UTF-8 序列被切成 1.5 个 UTF-16 码元，
  得到的是一串**合法但错误**的 CJK 码点。

**决定性证据**：把存储内容按码点十六进制打印，首码点序列是
`6556 7372 6F69 3A6E 2E31 0D30 530A`，按 UTF-16LE 读出来是
`"eV" "sr" "io" "n:" "1." "0\r" "\nS"` —— 正是 `"Version:1.0\r\n"` 的**字节对交换**。
另一条直观证据：Win32 直接读到的原始字节是
`56 65 72 73 69 6F 6E 3A 31 2E 30 0D 0A 53 74 61`，单字节 ASCII、无 NUL 间隔，
排除了 UTF-16 的可能。

**重要判别经验**：UTF-8 字节按 UTF-16 解码**不会**产生 U+FFFD，而是产生合法 CJK 码点
（实测 `hasCjk=True` 且 `hasFFFD=False`）。所以"有没有替换符"**不能**用来判断是否乱码，
必须断言内容里包含特定字符。

**修复**：新增 `DecodeHtmlBytes(byte[] bytes)`，先用「前 4 字节里第 2、4 字节是否为 0」
判断是不是 UTF-16，是则 `Encoding.Unicode`，否则 `Encoding.UTF8`。
`ReadHtml()` 改为按 `GlobalSize` + `Marshal.Copy` 取原始字节再解码，
`GlobalSize` 失败时才退回旧的 `PtrToStringUni`。

### 根因二：还原剪贴板时把 Word 的 COM 代理交回 OLE

`SelectionCapture` 划词取词的流程是「快照剪贴板 → 注入 Ctrl+C 复制选区 → 还原剪贴板」。

原来的 `SnapshotClipboard()` 用 `Clipboard.GetDataObject()`，Word 持有剪贴板时
返回的是**指向 Word 进程的 COM 代理**；`RestoreClipboard()` 再
`Clipboard.SetDataObject(saved, copy: true)`，等价于 `OleSetClipboard(代理)` +
`OleFlushClipboard()`。Flush 会**同步**要求源对象渲染它声明的**全部**格式
（Word 声明了 11 种，含 `Embed Source` / `ObjectLink` / `EnhancedMetafile`），
于是从我们的 STA 线程**重入 Word 的剪贴板代码**——而此刻 Word 刚被注入的 Ctrl+C
唤醒，可能仍在自己的剪贴板处理里 → `combase.dll` 访问违例。

**证据**：Windows 事件日志里三次崩溃完全一致
（`WINWORD combase.dll c0000005 0x08f46ddb`，20:34:58 / 20:35:27 / 20:37:29），
全部落在用户测试窗口内，且每次日志里都紧跟一条
`[selection] capture diag: seq ... copied=50 115ms`。

**修复**：`SnapshotClipboard()` 只取**纯值**（文本 / 冻结后的位图 / 文件列表 /
HTML 与 RTF 的原始字节），返回自包含的 `ClipboardSnapshot`；
`RestoreClipboard()` 用新建的 `DataObject` 重新放入，**绝不把外部 COM 代理交回 OLE**。

### 根因三（我自己引入的回归）：纯值还原丢了富格式

第一版修复只还原文本/图片/文件，实测还原后剪贴板格式变成
`UnicodeText,System.String,Text` —— `HTML Format` 和 `Rich Text Format` 都没了。
后果：用户先复制 Word 表格、再做一次划词取词，表格结构就丢，粘回去只剩纯文本。

我曾在阶段总结里把这个写成"有意的取舍"，**这个判断是错的**。
崩溃的成因是**COM 代理**，跟读取富格式字节没有关系。

**修复**：`ClipboardSnapshot` 增加 `byte[]? Html` / `byte[]? Rtf`；
`ReadRawFormat(uint format)` 走 Win32（`OpenClipboard` → `GetClipboardData` →
`GlobalSize` → `GlobalLock` → `Marshal.Copy`）拿**原始字节**，
不用 `Clipboard.GetData(fmt)`（它会把 HTML Format 解码成 string，再编码回去字节数可能变，
头部偏移随之失效）；还原时用 `MemoryStream` 原样放回。
上限 `MaxFormatSnapshotBytes = 8 MB`。

### 防复发

1. **不要用控制台打印中文来判断乱码。** 控制台代码页的错乱与真实数据损坏无法区分。
   必须打印码点十六进制，并断言内容包含特定字符。
2. **剪贴板格式的字节编码必须按格式分别处理。** `CF_UNICODETEXT` 是 UTF-16，
   `HTML Format` 是 UTF-8，`Rich Text Format` 是 ANSI。三者不能共用一个解码函数。
3. **绝不把外部进程的 COM 代理交回 `OleSetClipboard`。** 跨进程 COM 代理 + `OleFlushClipboard`
   的同步渲染会重入源进程，是稳定的崩溃源。快照必须是自包含的纯值。
4. **不要为了修崩溃而牺牲功能。** 先定位崩溃的**确切机制**（这里是 COM 代理重入），
   再针对机制修；把"丢失富格式"当成必要代价是偷懒，会引入新回归。
5. **验证 UI/行为必须用真实应用路径。** 反射调用内部方法能证明函数对，
   证明不了运行中的实例对；最终验收要跑 `_verify_live_*.ps1` 这类端到端脚本。

### 本轮操作陷阱

- **按文本锚点切片源码前，必须确认锚点在目标作用域内唯一。**
  用 `s.index("}\n")` 定位方法结尾时匹配到了内层嵌套 `}`，
  导致残留旧方法签名和孤儿 `catch`，编译报
  `CS1022 / CS8803 / CS0106`。改用完整方法签名或行号定位。
- **`io.open(..., encoding="utf-8-sig")` 写文件会加 BOM。**
  该文件原本无 BOM，写完要 `open(p,'wb').write(b[3:])` 剥掉。
  仓库里 18 个 `.cs` 有 BOM、45 个没有，是历史遗留，不要新增。
- **PowerShell 不能把 `UIntPtr` 直接转 `int`**（`GlobalSize` 的返回值），
  必须 `[int]([RawClip]::GlobalSize($h).ToUInt64())`。
- **PowerShell 函数必须在调用点之前定义**（执行期解析），否则报"无法识别的 cmdlet"。
- **`Clipboard.GetData('HTML Format')` 读回的是 `System.String`，不是 byte[]。**
  WPF 会把放进去的 `MemoryStream` 解码回字符串；要验证字节偏移必须用 Win32 `GetClipboardData`。
- **写回也会把内容重新放进剪贴板，被自己的监听器再捕获一次。**
  测试写回逻辑会额外产生 2 条历史条目，清理时不能假设只有 1 条。
- **改历史文件前必须先停进程。** 运行中的实例内存里持有条目列表，
  退出时会原样写回，覆盖磁盘上的修改。正确顺序：停进程 → 改文件 → 起进程，
  以启动日志的 `clips=N` 确认生效。

## 剪贴板预览与表格保真第二轮修复（2026-11-02 深夜）

### 现象

用户反馈四条（原文）：

> 1.截图有记录了，显示的是图片两个字，能不能以缩略图显示；2.在word里复制文字，
> 剪贴板里显示的是Nomal 0 ，点击粘贴不可用，会在剪贴板里重新生成一条正确的复制信息，
> 点击正确的信息可以粘贴，又会在剪贴板里生成一条新的复制信息。总之任何应用里复制的文字，
> 第一次显示的信息都不是复制内容。3.复制Excel表，也是第一次显示的信息不可用，
> 会重新生成一条可用的信息，但无表格样式。4.复制word表格可以正确使用，
> 但在剪贴板里显示的是首个单元的文字，能不能在剪贴板里也以缩略图的形式显示。

### 根因一：CF_HTML 的头部偏移是**字节偏移**，被当成字符偏移用

这是「Normal 0」和「Excel 无表格样式」的共同源头。

`HTML Format` 载荷的结构是：

```
Version:0.9\r\n
StartHTML:0000000105\r\n
EndHTML:00000040623\r\n
StartFragment:0000039666\r\n
EndFragment:0000040583\r\n
\r\n
<html>...<head><style>...</style></head><body><!--StartFragment-->...<!--EndFragment--></body></html>
```

**头部里的四个偏移全部是字节下标，不是字符下标。** 旧代码 `ExtractHtmlFragment` 把它们
当成 .NET string 的字符下标，用 `raw.Substring(start, end - start)` 去切。

Word 导出中文时会把汉字转成 `&#20813;&#36153;` 这种数字字符引用，整个载荷几乎全是 ASCII，
所以「字节数 / 字符数 ≈ 1.001」—— 平时差得不明显。但只要载荷里有任何多字节字符，误差就会累积；
实测 Word 表格的 `EndFragment:40583` 已经**大于**解码后的字符总长 40569：

- `start >= 0 && end > start && end <= raw.Length` 这个守卫直接失败
- 代码退到「跳过头部空行」的兜底路径
- 兜底路径从 Word 的 `<head>` 里切走了一大段 CSS
- `StripTags()` 之后剩下 `Normal 0 false false false EN-US ZH-CN X-NONE 7.8 磅`
- **这就是用户看到的「Normal 0」**

Excel 的载荷更极端：`<table>` 标签在 `StartFragment` **之前**（字节 1791 < 1915），
`</table>` 在 `EndFragment` **之后**（字节 2502 > 2482）。也就是说 **Excel 声明的「片段」
里根本没有表格外壳，只有裸的 `<col>`/`<tr>`/`<td>`**。只按声明范围切，粘回去自然没有表格。

实测三份真实载荷（`%TEMP%` 下）：

| 载荷 | 总字节 | `<table` 字节位 | StartFragment | EndFragment | `</table>` 字节位 | 片段含 `<table>` |
|---|---|---|---|---|---|---|
| Excel | 2534 | 1791 | 1915 | 2482 | 2502 | 否 |
| Word 表格 | 40623 | 39670 | 39666 | 40583 | 40571 | 是 |
| Word 文字 | 39811 | 无 | 39689 | 39771 | 无 | 否 |

### 根因二：`<style>` 块在 `<head>` 里，位于片段之外

只存片段就丢了样式。Excel 导出的 HTML 用 `class=xl65` 这类类名控制边框，
类定义全在 `<head><style>` 里，没有它粘出来就是无边框的纯文本。

修法：**额外存下 `<style>` 整块**（1–3 KB），写回时重新拼进 `<head>`。
不存完整文档（40 KB），因为每条都存全文会让存储翻倍。

### 根因三：`StripRtf` 不跳过 RTF 的「目标分组」

RTF 里 `{\fonttbl ...}`、`{\colortbl ...}`、`{\stylesheet ...}`、`{\info ...}`、
`{\*...}` 这些分组只有声明价值，正文一个字都没有。旧实现只删控制字和花括号，
字体表里的字体名被当成正文输出 —— 复制 Excel 表格后预览变成 `线;线;线;线; Line;线;`。

### 根因四：`\uNNNN` Unicode 转义被整段丢弃

这是本轮最严重的一条。Word/Excel 的中文经常整段用 `\uNNNN` 表示：

```
\uc2\u24207\'d0\'f2\u21495\'ba\'c5   →  序号
\u22995\'d0\'d5\u21517\'c3\'fb        →  姓名
```

旧代码把它当普通控制字跳过，表头「序号」「姓名」全丢，预览只剩 `1` `2`。
注意 `\uc2` 声明了后面跟 **2 个** `\'hh` 回退字符（`'d0'f2`），这些也必须一起跳过，
否则会被当作正文重复输出。

### 根因五：`\row` 与 `\par` 连用产生双换行

表格每行结束同时有 `\row` 和 `\par`，各自都转成 `\n` → 预览里每行之间多一个空行。

### 关键技巧：latin-1 做字节下标与字符下标的桥

`ExtractTableAware` 需要在整段载荷里搜 `<table` 标签，但载荷是 `byte[]`，
而 .NET 没有「在字节数组里搜 ASCII 字符串」的现成 API。

```csharp
string latin = Encoding.GetEncoding(28591).GetString(raw);
int open = latin.LastIndexOf("<table", start, StringComparison.OrdinalIgnoreCase);
int close = latin.IndexOf("</table>", end, StringComparison.OrdinalIgnoreCase);
byte[] expanded = Slice(raw, open, close + 8);
```

latin-1（代码页 28591）是单字节一一映射，**字符下标恒等于字节下标**，可以安全地
拿整段载荷当字符串搜标签、再按同组下标切回字节数组。

**在中文系统上绝不能用 UTF-8 字符串下标去切字节数组** —— 一个汉字占 3 字节，
下标立刻错位。另外 net48 没有 `Encoding.Latin1`（.NET 5+ 才有），必须用代码页号。

  像素偏移（不再写死 54），但**没有真实样本验证过**。

### 防复发

1. **凡是从剪贴板读的结构化载荷（CF_HTML、CF_RTF），一律按 `byte[]` 处理。**
   头部声明的偏移是字节偏移。转成 string 之后再切，迟早错位。
2. **`RegisterClipboardFormatW` 返回的 id 每个会话都不同**，必须运行时取，不能硬编码。
   实测过 49395 / 50107 / 50024 / 49409 四种值。
3. **P/Invoke `RegisterClipboardFormatW` 必须带 `CharSet = CharSet.Unicode`。**
   缺了会按 ANSI 传字符串，注册出**另一个** id，`GetClipboardData` 返回 0，
   表现得像「剪贴板上没有这个格式」。
4. **判断内容是否正确一律打印码点十六进制，不要看控制台输出。**
   控制台代码页错乱和真实损坏无法区分。本轮有两次误判都源于此
   （`Alpha beta gamma` 被当成乱码、`序号` 被当成乱码，实际都是对的）。
5. **派生字段（Preview / HtmlStyle / 缩略图）坏了不等于数据坏了。**
   先看 `Text` 是否完好，完好就可以重算，不必让用户重新复制。
6. **改 `clipboard.json` 前必须先停进程并轮询确认归零。**
   运行中的实例在内存里持有条目列表，退出时会原样写回，覆盖磁盘修改。

### 本轮操作陷阱

1. **`LoadThumbnail` 里 DIB 的像素偏移不能写死 54。** 54 只对「40 字节
   BITMAPINFOHEADER + 无调色板」成立。正确算法：
   `14 + biSize + paletteEntries * 4`，其中
   `paletteEntries = biClrUsed != 0 ? biClrUsed : (biBitCount <= 8 ? 1 << biBitCount : 0)`。
2. **`\uNNNN` 的参数可能带负号**（相对当前码位的偏移），要 `if (value < 0) value += 65536;`。
3. **`\ucN` 是局部状态，不能用静态字段** —— `StripRtf` 可能被多线程调用。
4. **PowerShell 5.1 读无 BOM 的 `.ps1` 按 ANSI 解码**，含中文的脚本会抛
   `表达式中包含意外的标记` / `字符串缺少终止符`。用 Python 写脚本时加
   `encoding='utf-8-sig'`。
5. **`ScrollPattern.Scroll()` 对 `ClipboardList` 抛 `InvalidOperationException`，
   但 `SetScrollPercent(NoScroll, pct)` 可用。**
6. **`$TEMP` 在 bash 里是 `/tmp`，Python 的 `os.path` 不认 `/tmp`。**
   用 `os.path.join(os.environ['TEMP'], ...)` 或 `tempfile.gettempdir()`。

#### 1. 用 Application 级 DynamicResource，不用依赖属性

## 助手页缩放上限锁定 1.0（2026-11-03 晚）

### 现象

用户（2026-11-03）提出：「我希望所有助手页面内容最大保持 1.0」。

背景是设置里有个「助手页加宽时字体等比放大」的开关（2026-10-31 加的）。开着它
点「加宽」时，网页缩放 = 站点基准 × 宽度乘数，DeepSeek / 千问这类基准本来是
1.00 的站点会被一并放大到 1.55 —— 字变大、每屏能看的内容反而更少，与「加宽是
为了看更多内容」的初衷相反。

### 根因

`AssistantService.EffectiveZoomFor()` 把结果夹在 `[0.1, 2.0]`：

```csharp
double zoom = ZoomFor(provider) * _widthScale;
if (zoom < 0.1) zoom = 0.1;
if (zoom > 2.0) zoom = 2.0;
```

2.0 是「WebView2 ZoomFactor 能接受的最大值」，不是产品上想要的上限。宽度乘数对
**所有**站点一视同仁地乘上去，没有「本来就不小就别再放」的分支。

实测证据（修复前日志）：

```
21:14:04.068 [assistant] width scale -> 1.55
21:14:04.085 [assistant] zoom deepseek = 1.55 (base 1.00 x scale 1.55)
```

### 修复

1. `src/QuickDrawer/Assistant/AssistantService.cs`
   - 新增常量 `public const double MaxZoom = 1.0;`（带完整注释说明为什么是 1.0
     而不是 2.0）
   - `EffectiveZoomFor()` 的 `if (zoom > 2.0) zoom = 2.0;` 改为
     `if (zoom > MaxZoom) zoom = MaxZoom;`，下界 0.1 保留（低于 0.1 会被
     WebView2 静默归一化）
2. `src/QuickDrawer/Config.cs`
   - `ZoomScaleWithWidth` 的注释改写：说明结果上限固定 1.0，所以只有基准低于
     1.0 的站点会真的变大
3. `src/QuickDrawer/SettingsWindow.xaml`
   - 复选框文案「助手页加宽时字体等比放大」→「助手页加宽时把小号站点补到 1.0」
   - 提示文案改为「缩放上限固定 1.0。开启后加宽时只把偏小的站点（Kimi 0.9、
     智谱 0.55）补到 1.0 为止；DeepSeek / 千问本来就是 1.0，字号不变，只是显示
     更多内容」

修复脚本 `probe/_fix_zoom_cap.py`。

### 为什么这么改（取舍）

- **不改宽度乘数的算法本身**。乘数在正常宽度下恒为 1.0，只有加宽时才 >1，改了
  反而会牵连「不进助手页也重算」的路径。
- **不按站点白名单跳过**。乘积后统一夹到 1.0 更简单，而且天然满足用户另一句潜
  台词「最大保持 1.0」——哪怕以后有人手动把某个站点的基准配成 1.3，也会被夹回
  1.0，不会出现「内容被放大」的意外。
- **下界仍是 0.1**。智谱 0.55 × 1.55 = 0.8525 落在区间内，保留它的原样；只有真
  正偏小的才被往上补。

2. **乘数类逻辑要问「谁不该被乘」**。`base × scale` 对 4 个站点一模一样地作用，

   乘数前先把「对每个输入意味着什么」列成表。
3. **验证「某值不变」要靠「该打的日志不再出现」**，不能只靠「日志里的数字是

4. **UI 文案必须跟着语义改**。开关名还叫「字体等比放大」而行为已经变成「只补

### 操作陷阱

1. **`AssistantService.cs` 是 CRLF，`Config.cs` 和 `SettingsWindow.xaml` 是 LF**。

   直接失败，一行都没写进去。
2. **UIA 找按钮要用 `x:Name`（`AssistantWidenButton`），不是

   `ERROR: AssistantWiden not found`。
3. **四个站点 chip 的 `x:Name` 是 `ChipDeepSeek` / `ChipQwen` / `ChipKimi` /
   `ChipGlm`** —— 智谱是 `ChipGlm` 不是 `ChipChatGlm`（`Tag` 才是 `chatglm`）。
4. **加宽是有状态的**。脚本跑完面板停在 620 宽，`config.json` 的 `dock.width`
   仍是 400（`widenWidth` 不落盘），下次启动回到 400 宽。验证脚本要么显式复位
   （再点一次加宽），要么接受这个状态。

### 需求

用户原话（2026-11-03）：

> 在面板的最底下我想要一行仪表盘，显示cpu/内存/网速/温度，点击cpu打开任务管理器

### 现象与设计取舍

面板底部新加一行固定高度（`Auto`）的仪表盘，四格横排：`CPU 1%`、`内存 74%`、
`网速 106K↓ 23K↑`、`温度 —`。只有 CPU 一格可点（点击打开任务管理器），其余三格
是纯文本。鼠标悬停 CPU 格才浮出底色与 ToolTip，外观与旁边的静态格保持一致。

温度一项**在本机拿不到真实值**，显示破折号 `—` 并在 ToolTip 里说明原因。
这是如实降级，不是未实现。

### 温度不可用的取证（6 条路径全部失败）

环境：AMD Ryzen 7 5800H / Windows 11 build 10.0.22621 / 非管理员。

| 路径 | 结果 |
|---|---|
| `Get-CimInstance -Namespace root/WMI -ClassName MSAcpi_ThermalZoneTemperature` | 类存在，查询实例抛「不支持」 |
| `Get-WmiObject -Namespace root/WMI -Class MSAcpi_ThermalZoneTemperature` | 同样抛「不支持」 |
| `ManagementScope("\\.\root\WMI")` + `ObjectQuery` | 构造 scope 时就抛「无效的参数」 |
| PerfMon `\Thermal Zone Information(*)\Temperature` | `-ListSet` 能列出 4 条路径，但 `Get-Counter` 连采 3 次都是 **0 个实例** |
| `Win32_PerfFormattedData_Counters_ThermalZoneInformation` | count = 0 |
| `Win32_TemperatureProbe` | 无实例 |

第三方工具一个都没装（LibreHardwareMonitor / OpenHardwareMonitor / HWiNFO64 /
Core Temp 的 `Test-Path` 全是 `False`）。

**结论：本机 ACPI 没有向系统暴露热区温度，是主板 / 驱动层限制。**
不引入第三方内核驱动（需管理员 + 驱动签名）就拿不到。所以温度格永不显示假数字。

### 实现

新增 `src/QuickDrawer/DashboardSampler.cs`（`internal sealed class`）：

- **CPU** —— `GetSystemTimes(out idle, out kernel, out user)`。
  **kernel 时间已经包含 idle**（Win32 文档明确），所以
  `total = kernelDelta + userDelta`，`busy = total - idleDelta`。
  三项相加会把 idle 算两遍，CPU 百分比永远偏低。
- **内存** —— `GlobalMemoryStatusEx`。`dwLength` 必须由调用方先赋
  `Marshal.SizeOf<MEMORYSTATUSEX>()`，否则函数直接返回 false。
- **网速** —— `NetworkInterface.GetAllNetworkInterfaces()` 求和
  `GetIPv4Statistics().BytesReceived/BytesSent`。网卡列表**缓存 10 秒**
  （枚举比读计数器贵得多）；逐网卡 try/catch（网卡刚断开会抛）；
  差值为负时按 0 处理（网卡重连后计数器会归零）。
- **温度** —— 后台 `ThreadPool.QueueUserWorkItem` 读一次，最多试 3 次后放弃。
  `Convert.ToDouble(raw) / 10.0 - 273.15`（ACPI 以 0.1 K 为单位），
  取所有实例中最大的合法值（`0 < c < 130`）。

**为什么不用 `PerformanceCounter`**：首次实例化 200–800 ms，放 UI 线程会卡住
滑出动画；而且本机 `\Thermal Zone Information` 计数器集存在但 0 个实例，
走 PDH 只是多一条永远拿不到数据的路径。

`src/QuickDrawer/Native/Native.cs` 追加 `GetSystemTimes`、`MEMORYSTATUSEX`、
`GlobalMemoryStatusEx`、`TryGetMemoryStatus`。

`src/QuickDrawer/QuickDrawer.csproj` 加 `<Reference Include="System.Management" />`
（net48 用框架程序集，**不要装 NuGet 包**，那个是给 .NET Core 的）。

### 布局改动（关键：Row 5）

`src/QuickDrawer/DrawerWindow.xaml` 的 `RootGrid` 原来 5 行，`BottomAreaRow`（Row 4）
是 `*`。新增 `<RowDefinition x:Name="DashboardRow" Height="Auto"/>` 作为 **Row 5**，
`BottomAreaRow` 保持 `*`。

**`ComputePathAreaMaxHeight()` 里的行索引累加必须补上 5**：

```csharp
// 改前
foreach (int index in new[] { 0, 1, 3 })
// 改后
foreach (int index in new[] { 0, 1, 3, 5 })
```

漏掉 5 会让目录区高度上限多算一行，拖到极限时便签区会被仪表盘压掉。

### 生命周期

- `StartDashboard()` 放在 `ShowAnimated()` 里、打 `"show animating"` 日志之前。
- `StopDashboard()` 放在 `HideAnimated()` 的 `anim.Completed` 回调里、
  `_handle?.ShowForPanel()` 之后、打 `"drawer collapsed"` 之前。
- 计时器 1 秒一帧，面板收起即停 —— 面板收着的时候不采样。

### 防复发

1. **`GetSystemTimes` 的 kernel 时间包含 idle**。判 CPU 占用用
   `total - idle`，不能 `idle + kernel + user`。
2. **`GlobalMemoryStatusEx` 的 `dwLength` 必须调用方填**，忘了填直接返回 false，
   且不设 `LastError`，排起来很费时间。
3. **`RootGrid` 加行之后，凡是硬编码行索引的地方都要检查**。
   `ComputePathAreaMaxHeight()` 的 `new[] { 0, 1, 3 }` 就是典型。
4. **温度不要造假**。本机取不到就显示 `—` 并在 ToolTip 说明，比显示一个固定
   数字（比如 45°C）诚实得多，也不会让用户误判散热有问题。
5. **采样器不要放 UI 线程做重活**。`PerformanceCounter` 首次实例化 200–800 ms，
   放滑出动画路径上会肉眼可见地卡。
6. **面板收起时必须停掉计时器**。否则一个隐藏窗口仍在每秒唤醒一次，
   笔记本电池上很浪费。

### 操作陷阱

1. **Windows 命令的 `/参数` 在 bash 里会被 MSYS 当成路径转换**。
   `taskkill /PID 14324 /F` 实际执行成了
   `taskkill 'C:/Users/%USER%/.dsh/profiles/.../PID' 14324 /F`，报
   「无效参数/选项」。要用 `MSYS_NO_PATHCONV=1 taskkill ...` 或直接走 PowerShell。
2. **任务管理器以更高完整性级别运行，普通权限杀不掉**。
   `Stop-Process -Force` 报「拒绝访问」，`CloseMainWindow()` 也无效。
   测试打开它之后只能请用户手动关，或在提权会话里关。
3. **UIA 找按钮一律用 `x:Name`**。面板钉住按钮是 `PinPanelButton`，
   仪表盘的 CPU 格是 `DashCpu`。
4. **解钉面板会立刻触发自动收起**，之后的截图 / UIA 操作全部找不到抽屉窗口。
   验证完要记得把 `dock.pinPanel` 恢复成 `true`（改 `config.json` 需先停进程，
   否则退出时会被内存里的旧值覆盖）。
5. **`App.ShowNotice` 是 `(string, TimeSpan?)` 两参签名**，
   传一个 string 报 `CS1503 参数 2 无法从 string 转换为 System.TimeSpan`。

## 剪贴板偶发漏记：6 条根因 + 三重还原守卫（2026-11-05 晚）

### 现象

用户原话（2026-11-05）：

> 剪贴板不能100%记录复制的信息，有时复制了信息，可以粘贴使用，但剪贴板里没有显示

关键点：**能粘贴**说明剪贴板本身有内容，**丢的是"记录"**。这个区分贯穿了整个排查
—— 只看剪贴板内容永远复现不出来，必须查历史条目。

### 取证：生产日志统计（1,642,887 字节，约 670 次拖拽）

```
[clipboard] capture skipped (suppressed by selection watcher)  1658
[clipboard] captured ...                                       311
[clipboard] gave up reading after retries                       55
[clipboard] read skipped: previous read still running           23
[clipboard] capture failed                                       8
[clipboard] evicted ...                                         58
[selection] selection captured                                 337
[selection] capture diag                                       500
[selection] drag end at                                        664
```

抑制偏移直方图（被吞的通知距最近一次 `drag end` / 截图落地的时间）：

| 距上次划词/截图 | 0–0.15s | 0.15–0.4s | 0.4–1.0s | 1.0–2.0s | 2.0–2.6s |
| --- | --- | --- | --- | --- | --- |
| 次数 | 710 | 100 | 308 | 515 | 29 |

**670 次拖拽中有 344 次在 0.4 秒之后仍有被吞的通知** —— 说明抑制窗口开得太长、
覆盖面远超它真正需要保护的时段。

### 6 条根因（全部有行号依据）

| # | 根因 | 位置 |
| --- | --- | --- |
| 1 | 抑制窗口内整段丢弃，用户自己按的 Ctrl+C 也被吞 | `ClipboardService.cs:354-360` |
| 2 | 读闸门 5 秒超时即永久丢弃 | `ClipboardService.cs:366` |
| 3 | 固定 80ms 首延迟，这期间再复制一次就丢前一份 | `ReadWithRetryAsync()` |
| 4 | 只认 `CF_UNICODETEXT`，只给 `CF_TEXT`/`CF_OEMTEXT` 的程序 100% 读不到 | `ClipboardService.cs:545` |
| 5 | 文件分支失败断路，`ReadFiles()` 返回 null 时同存文本/图片一起丢 | `ClipboardService.cs:494-496` |
| 6 | 去重静默无日志，"复制了却没有"无法区分是去重还是没读到 | `ClipboardService.cs:392-396` |

第 1 条的窗口由两处武装：`Selection/SelectionCapture.cs:139`（2500ms）与
`Assistant/AssistantService.cs:545`（3000ms）。窗口内**任何**剪贴板变化都是
`return`，包括用户手动的 Ctrl+C。

### 另外发现的独立缺陷：划词还原会覆盖用户剪贴板内容

这条不是"漏记"，是**直接覆盖** —— 更严重。

`Selection/SelectionCapture.cs:199` 的 `finally { RestoreClipboard(saved, previousText); }`
无条件把拖拽前的快照写回，**不检查这期间剪贴板是否已被别人改过**。

决定性实验（`probe/_clip_clobber2.ps1`）：拖拽触发捕获 → 抑制窗口内写
`QDMARK-211156902` → 等 4 秒读回：

```
BEFORE=[QDTEST2-210645-ansi-only]
SET marker at 21:11:56.934 (try 0)
AFTER=[QDTEST2-210645-ansi-only]
RESULT=CLOBBERED
```

用户内容既不在剪贴板、也不在历史里 —— **这正是用户报的症状**。
`Assistant/AssistantService.cs:695-716` 的 `RestoreClipboard(IDataObject?)` 有同样问题。

### 修复

#### A. 6 条根因（`src/QuickDrawer/ClipboardService.cs` + `Native/Native.cs`）

1. **抑制改为"延后补读"而不是丢弃**：抑制期内只记下 `GetClipboardSequenceNumber()` 到
   `_deferredSeq`，再 `ScheduleSuppressReconcile()` 起一个后台任务，等抑制真正过期
   （`_suppressUntilUtc` 之后 +30ms）再比对序列号决定是否补读。
   新增字段 `_deferredSeq` / `_reconcileScheduled` / `_gateMisses`。
2. **读闸门 5s → 20s**，超时后按 200ms 退避重试最多 10 次，超过才记
   `read gate busy after 10 retries, giving up`。
3. **删掉固定 80ms 首延迟**：第 0 次立即读，失败才按 `{ 60, 120, 240, 480 }` 退避。
4. **ANSI 回退**：`Native.cs` 新增 `CF_TEXT = 1` / `CF_OEMTEXT = 7`；格式探测里
   `hasAnsiText` 与 `hasText` 并列为文本分支条件；`ReadText()` 拿不到
   `CF_UNICODETEXT` 时依次试这两个并用 `Marshal.PtrToStringAnsi` 解码。
5. **文件分支不再断路**：`ClipEntry? files = ReadFiles(); if (files is not null) return files;`
   —— 读不到就继续走后面的文本/图片分支。
6. **去重加日志**：`dedup: identical content already in history`。

#### B. 三重还原守卫（`SelectionCapture.RestoreClipboard`）

守卫按顺序排列，**任一条命中就放弃还原**（放弃的代价只是剪贴板留着用户选中的文字，
这本就是 Ctrl+C 的正常结果；覆盖用户内容则是数据丢失）。

演进过程（三次都被实测推翻，值得记住）：

| 代 | 信号 | 为什么不够 |
| --- | --- | --- |
| 1 | 剪贴板序列号 `seqAfterCopy` | 采样点在"轮询发现变化那一刻"，用户若在这**之前**已写入，采到的已是用户的序列号 |
| 2 | 内容比对（`currentText != copiedText`） | 只能识别"读到之后被改"。实测 `copied=16` 正是抢先写入的 marker 长度 —— 程序把 marker 当成了用户选中的文字 |
| 3 | **剪贴板所有者进程** `GetClipboardOwner()` | 有效。所有者就是写入方进程，能从根上区分"谁写的" |

最终实现（所有者检查是**第一道闸**，排在内容比对之前）：

```csharp
uint ownerPid = 0;
IntPtr ownerHwnd = NativeMethods.GetClipboardOwner();
int ownerError = ownerHwnd == IntPtr.Zero ? Marshal.GetLastWin32Error() : 0;
if (ownerHwnd != IntPtr.Zero)
{
    NativeMethods.GetWindowThreadProcessId(ownerHwnd, out ownerPid);
}

if (ownerHwnd == IntPtr.Zero || (ownerPid != 0 && ownerPid != fgPid))
{
    DiagLog.Write("selection",
        $"restore skipped: clipboard owner not ours (hwnd={ownerHwnd} ownerPid={ownerPid} fgPid={fgPid} err={ownerError})");
    return;
}
```

**fail-closed 取舍**：查不到所有者（`ownerHwnd == IntPtr.Zero`）时也放弃还原。
最初写成 `ownerPid != 0 && ownerPid != fgPid`（查不到就放行），是错的 ——
别的进程高频写剪贴板时 `GetClipboardOwner` 常返回 NULL（对方正开着剪贴板），
放行等于守卫失效。

`Native/Native.cs` 的 `GetClipboardOwner` 补上 `SetLastError = true`（剪贴板被占用时
返回 NULL 且 last error = 5 ACCESS_DENIED，用于取证）。

`Assistant/AssistantService.cs` 同样加 `seqAfterWrite` 守卫（新增

## 面板收起会激活已最小化的窗口（2026-11-05 深夜）

### 现象（用户原话，m07888）

> 面板钉住再关闭后收起，会将已最小化的窗口激活显示，无法保持当前激活窗口状态。
> 助手页点击截图按钮面板收起后也会激活已最小化的窗口

两个看起来无关的场景，实测是两条**独立**的触发路径。

### 根因 1：`WindowPushOut.End()` 用 `SetWindowPlacement` 还原

面板钉住时，`WindowPushOut` 会把被压住的窗口左移，并把**改动前**的
`WINDOWPLACEMENT` 存进 `_saved`。取消固定 / 面板收起时 `End()` 原样还原。

问题在于存档里的 `showCmd`：如果那个窗口当时是 `SW_SHOWMINIMIZED`，
`SetWindowPlacement` 会**把它显示出来并激活** —— 这个 API 没有"还原但不激活"的变体。

`End()` 原本只保护了一侧：
```csharp
if (NativeMethods.IsZoomed(kv.Key)) { skipped++; continue; }   // 用户又最大化了 → 跳过
```
没有对称地保护"用户又最小化了"。

### 根因 2：`HideAnimated()` / 截图遮罩的前台重选

`HideAnimated()` 的 `anim.Completed` 里直接 `base.Hide()`。窗口消失后 Windows
要把前台交给 Z 序下一个候选；此时若桌面上可见窗口都不在前台候选里，
系统会**恢复一个最小化窗口**来接收前台。

助手页截图路径更明显：`TakeScreenshotAsync()` 先 `HideAnimated()`，
再弹全屏模态遮罩 `ScreenshotOverlay`（`Topmost = true`）。遮罩关闭时同样触发一次前台重选。

对比一下：滑出侧 `ShowAnimated()` 早就有"还原前台"的逻辑，**收起侧一片空白**。

### 验证：先证明 API 能做到，再改代码

`probe/_minpos_probe2.ps1`（对最小化窗口强制 `showCmd = SW_SHOWMINIMIZED` 再 `SetWindowPlacement`）：
```

after minimize  : showCmd=2 iconic=True  normal=130,130 600x400
after move      : showCmd=2 iconic=True  normal=100,100 500x500  ret=True
after restore   : showCmd=2 iconic=True  normal=130,130 600x400  ret=True
fg before set   : 0x20202
fg after set    : 0x20202
VERDICT=STILL-MINIMIZED
normalRestored=YES
```
→ 能改回 `rcNormalPosition`、窗口仍最小化、前台不动。**方案成立才动代码。**

反向对照 `probe/_minpos_probe.ps1`：对最小化窗口调
`SetWindowPos(... SWP_NOZORDER | SWP_NOACTIVATE)` **不会**改写 `rcNormalPosition`
（`normalRectChanged=NO`），所以不能用它修几何 —— 只能走 `SetWindowPlacement`。

### 修复

**1. `src/QuickDrawer/WindowPushOut.cs` 的 `End()`** —— 补上最小化分支：
```csharp
if (NativeMethods.IsIconic(kv.Key))
{
    NativeMethods.WINDOWPLACEMENT minimizedPl = kv.Value;
    minimizedPl.showCmd = NativeMethods.SW_SHOWMINIMIZED;   // 关键：不让它弹出来
    NativeMethods.SetWindowPlacement(kv.Key, ref minimizedPl);
    minimized++;
    continue;
}
```
`src/QuickDrawer/Native/Native.cs` 补 `SW_SHOWMINIMIZED = 2`。
日志补上最小化窗口的名字和失败 errno，汇总行加 `, kept N minimized`。

**2. `src/QuickDrawer/DrawerWindow.xaml.cs` 的 `HideAnimated()`** ——
在 `base.Hide()` **之前**把前台交还：
```csharp
HandForegroundBack("hide");
base.Hide();
```
提前交还，系统就不会在窗口消失后去做那一次前台重选。
`RestoreForeground()` 里做了四道保护：目标是自己/自己子窗口、目标已销毁、目标已在前台、
**目标是最小化窗口** —— 最后一条尤其重要，否则我们自己去激活别人。

**3. `TakeScreenshotAsync()`** —— 遮罩关闭后补一次 `RestoreForeground(_pasteTarget, "shot")`。

### 防复发

1. **`SetWindowPlacement` 是"激活"操作，不是"摆放"操作。** 想还原几何又不想打扰用户，
   必须显式把 `showCmd` 改成 `SW_SHOWMINIMIZED` / `SW_SHOWNOACTIVATE`。
   存档里 `showCmd` 是多少，还原时就会把窗口摆成什么样 —— 包括弹出来。
2. **凡是"还原用户窗口"的地方，都要对称地检查"用户在这期间改过没有"。**
   有 `IsZoomed` 保护就必须有 `IsIconic` 保护，思路是"用户的手比我们的存档新"。
3. **窗口 `Hide()` 之后再处理前台就晚了。** 系统的前台重选发生在窗口消失的那一刻，
   所以交还前台的代码必须在 `Hide()` **之前**。
4. **`Show()` / `Hide()` / 模态窗关闭都会触发前台重选**，凡是走这三条路的地方都要检查一遍。
   滑出侧早在 `ShowAnimated()` 里处理过，收起侧却漏了整整一年 —— 因为"没显示窗口"看起来不像会抢焦点。
5. **验收脚本必须让被测窗口真的落在候选区。** 前三版 `_minfix_test*.ps1` 因为漏写
   `$form.StartPosition = 'Manual'`，窗口落在 `52,52`，pushout 从未动它，
   `VERDICT=STILL-MINIMIZED` 是平凡绿 —— 假阴性比没测更危险。判据是 `MOVED=YES`。
6. **UIA 里标签页是 `RadioButton`，只有 `SelectionItemPattern`。**
   对 `TabAssistant` 用 `InvokePattern` 会抛"不支持的模式"；
   脚本若把异常吞掉就会打印 `True` 骗人。**点标签页用 `Select()`，点按钮用 `Invoke()`。**

## 取消钉住后不再还原窗口：保持当前布局（2026-11-06）

### 现象

用户原话（m08344）：

> 面板取消钉住后收起，会将之前被弹开的窗口恢复到原来位置，不要让被弹开的窗口再回到原来位置，保持当前布局。

这是对上一节（「面板收起会激活已最小化的窗口」）行为的**反转要求**。
上一节把"被弹开的窗口在取消钉住时还原到原位"当成正确行为，只修补了
"还原时不要激活最小化窗口"这一个副作用。用户现在明确说：**不要还原**。

> **本节推翻上一节的描述。** 上一节验收表里的
> 「被你最小化的窗口只悄悄修回位置」、`probe/_minpos_probe2.ps1` 那条
> `normalRestored=YES` 的证据，都是围绕"仍然还原几何"设计的。
> 从 2026-11-06 起，`End()` **一次也不调用 `SetWindowPlacement`**，
> 上一节的 `IsZoomed` / `IsIconic` 两道保护连同它们保护的还原动作一起删除了。
> 上一节仍然有效的部分是：**收起/遮罩关闭时不抢前台**（`HandForegroundBack`），那部分保留。

### 根因（不是 bug，是设计选择错了）

`WindowPushOut` 的工作方式是"把被面板压住的窗口弹出遮挡区"，为此它在 `Apply()` 里
用 `GetWindowPlacement` 把每个窗口**改动前**的摆放存进 `_saved`，等面板收起时
`End()` 逐条 `SetWindowPlacement` 还原。

这套对称设计的问题：**用户已经把那批窗口当成"新布局"在用了。**
钉住面板 → 一堆窗口被左移 → 用户在这个布局下继续工作 → 取消钉住 →

## 路径项图标缩小到与文字等高（2026-11-06）

### 现象

用户原话（m08752）：

> 调整路径下添加的快捷项的图标大小，图标与文字保持高度一致。我的电脑除外。

改前像素实测（截图 `%TEMP%\qd_path_icons.png`，400x1032，背景 `#F2F3F6`）：路径项图标统一是 `20x20` 的 Image，
文件夹图标实际墨迹高 **14px**、文件图标 **15px**（「离线PDF工具箱V7.1」的 Edge 图标撑到 21px），
而旁边一行文字（列表模式 13px 字号）墨迹高只有 **12px**。图标比文字高出一整圈，视觉上很跳。

### 根因

图标尺寸被硬编码成 20，与字号没有任何关系，三处各写一遍：

| 位置 | 用途 |
| --- | --- |
| `src/QuickDrawer/DrawerWindow.xaml:526` | DataTemplate 里的占位 Image（`PathItem_Loaded` 替换成下面两种行之前短暂存在） |
| `src/QuickDrawer/DrawerWindow.xaml.cs:3744` `BuildIconRow()` | 图标模式（标签 `FontSize = 12`） |
| `src/QuickDrawer/DrawerWindow.xaml.cs:3772` `BuildListRow()` | 列表模式（名称 `FontSize = 13`，左图标 + 右文字） |

另一个关键事实：`src/QuickDrawer/DrawerWindow.xaml.cs:1696` `PathItem_Loaded` 里
`bool drive = vm.Model.Kind == "drive"; bool listMode = _config.Layout.Paths == "list" && !drive;`
—— **盘符项永远走 `BuildIconRow`**，所以「我的电脑除外」只需要在图标行里按 `Kind == "drive"` 判断，不用管列表模式。

### 修复

`src/QuickDrawer/DrawerWindow.xaml.cs`，在 `BuildIconRow` 之前新增两个成员：

```csharp
private static double PathIconBox(double fontSize) => fontSize + 4;
private const double DriveIconBox = 20;
```

`BuildIconRow` / `BuildListRow` 各自按字号算方框（12 → 16、13 → 17），盘符两处都固定用 `DriveIconBox`。
`src/QuickDrawer/DrawerWindow.xaml:526` 的占位 Image 改成 `Width="17" Height="17"`（占位按列表模式的 13 号字算）。

**为什么是「字号 + 4」**：中文字形的墨迹高大约等于字号（13px 字实际 12px 墨迹），图标四周总要留一圈呼吸，
+4 是让 32px 源图缩到 16/17px 后墨迹落在 12–13px、正好与文字齐平。改前 20px 方框对应墨迹 14–15px，
比文字高 2–3px，就是用户说的"不一致"。

### 验证（两种布局模式都测）

尺寸吻合。放大 10 倍肉眼确认图形与 exe 一致。

**任务栏：不适用。** `DrawerWindow.xaml:10` 是 `ShowInTaskbar="False"`，QuickDrawer
本来就不创建任务栏按钮，托盘是它唯一的常驻入口。

### 六条防复发

1. **图标有两份实现，改一处必须同时改另一处**：`assets/QuickDrawer.ico`（文件/资源管理器/exe）
   与 `TrayIcon.CreateTrayHIcon()`（托盘运行时）。它们是两套独立代码，不是加载同一个文件。
   改完只验其中一个，另一个就是旧样子。
2. **判据选错会把好文件判成坏的**：`Icon.ToBitmap()` 对 PNG 帧抛「参数超出范围」，
   但**现网在用的** ico 同样失败 —— 因为它 9 帧全是 PNG 帧，.NET Framework 不支持。
   换新文件前先用旧文件跑同一套测试做对照，能立刻识别是"文件坏了"还是"工具不支持"。
3. **`Image.FromHbitmap(LoadImage 的返回值)` 不可用**：LoadImage 返回共享 DIB 段，
   GDI+ 不能接管，报「GDI+ 中发生一般性错误」。测图标要用
   `LoadImage(IMAGE_ICON) → HICON → DrawIconEx 到 32bpp 位图`，这才是系统真实渲染路径。
4. **16px 是第一判据，不是 256px**：第一轮 6 个方案在 1024px 下都好看，
   实渲染到 16px 后细线消失、箭头糊成一坨、描边连成一片。以后出新图标一律先出 16px 实渲染。
5. **Win11 托盘默认折叠**，直接截任务栏右下角看不到自己的图标。要点开 `^` 展开区再截；
   `^` 的位置每次可能有几像素偏差，先截图量出绝对坐标再点。
6. **`src/QuickDrawer/TrayIcon.cs` 是 CRLF**。用含 `\r\n` 的锚点做 `count()` 会得到 0，
   报 `AssertionError: anchor matched 0 times`。改法：
   读字节 → `decode().replace("\r\n","\n")` → 匹配替换 →
   `replace("\n","\r\n")` → `open(...,"wb")` 写回。

## 发布 1.0.0 到 GitHub：SSH 验签失败、winget 挂死、gh 不认系统代理（2026-11-07）

### 现象

本地仓库两个 commit 就绪（174 个文件 / worktree clean），要推送到 GitHub。三条路依次失败：

1. **SSH 推送**：`git push` 报 `git@github.com: Permission denied (publickey).`，
   但公钥已经加到账号里、`~/.ssh/config` 也指定了 `IdentityFile`。
2. **`winget install --id GitHub.cli --exact`**：挂起 18 分钟没有任何输出。
3. **`gh auth login --web`**：终端打印出设备码之后进程直接消失，
   `%APPDATA%\GitHub CLI` 目录**根本没被创建**，`gh auth status` 一直是
   `You are not logged into any GitHub hosts`。

### 根因（三条独立原因，逐条有证据）

**1. SSH 卡在 hostbound 签名验签环节，不是密钥没加对。**

`ssh -vvv -o BatchMode=yes -T git@github.com` 的输出里同时出现这三行：

```
debug1: Server accepts key: C:/Users/zhouh/.ssh/id_ed25519_quickdrawer ED25519 SHA256:cC2ZtN8nxEZAzordiy55OyTzAJ9DW8RzBPhgTr5I7sA explicit
debug3: sign_and_send_pubkey: using publickey-hostbound-v00@openssh.com with ED25519 SHA256:cC2ZtN8n...
debug3: sign_and_send_pubkey: signing using ssh-ed25519 SHA256:cC2ZtN8n...
git@github.com: Permission denied (publickey).
```

"Server accepts key" 说明服务端认得这个公钥，随后客户端改用
`publickey-hostbound-v00@openssh.com` 扩展签名，服务端验签失败。

排除法用的三条证据：
- 主机密钥 `ecdsa-sha2-nistp256 SHA256:p2QAMXNIC1TJYWeIOttrVc98/R1BUFWu3/LiyKgUfQM`
  是 GitHub 真身前缀 → 排除中间人劫持。
- `ssh -p 443 git@ssh.github.com` 同样 `Permission denied (publickey)` → 排除 22 端口被拦。
- 本地 `ssh-keygen -lf` 算出的指纹与 `~/.ssh/config` 指向的私钥一致 → 排除用错密钥。

具体是什么版本的 OpenSSH 与服务端在这个扩展上握手失败，**没有查清**。
本项目最终放弃 SSH，改走 HTTPS + token。

**2. winget 挂死是因为它在等一个没提权的 UAC 弹窗。**

`Get-Process` 看到 `msiexec`(pid 21016) 一直存活，`Stop-Process -Force` 报「拒绝访问」。
这不是下载慢，是安装器停在提权确认那一步，而当前会话不是管理员。

**3. `gh`（Go 程序）不读 Windows 的 IE 代理设置。**

- 注册表：`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`
  里 `ProxyEnable=1`、`ProxyServer=127.0.0.1:3067`。
- 环境变量 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` **全空**。
- `Invoke-WebRequest`（走 IE 代理）访问 `https://github.com` 三次 HEAD 全 200；
  用无效 client_id POST `https://github.com/login/oauth/access_token`
  返回规范的 `{"error":"incorrect_client_credentials",...}` —— 说明**经代理这个端点完全可达**。
- 而 `gh` 直连 `20.205.243.166:443`，报：
  `Post "https://github.com/login/oauth/access_token": ... wsarecv: A connection attempt failed ...`

Go 的 `http.ProxyFromEnvironment` 只认 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量，
不读 WinINET 配置。所以浏览器能打开 GitHub，`gh` 却连不上。

**4. `gh auth login --web` 静默退出，是因为它需要一个真交互式终端。**

非交互进程里 `--web` 打印完设备码就被终止；设备流本身没问题，缺的是那个 TTY。

### 验证方法

探针脚本都在 `probe/`：
- SSH 诊断：`ssh -vvv -o BatchMode=yes -T git@github.com 2>&1`，
  重点看 `Server accepts key` 之后是否出现 `Authenticated`。
- 代理连通性：拿一个**故意错误**的 `client_id` POST 到
  `https://github.com/login/oauth/access_token`，能拿回 JSON 错误体就说明链路通
  （超时才是链路问题）。
- 判断 `gh` 到底走没走代理：`gh` 失败时的报错里会带直连 IP（`20.205.243.166`），
  带代理时不会出现这个 IP。

### 修复

1. **`gh` 用官方 zip 免安装**，绕开 winget / UAC：
   `https://github.com/cli/cli/releases/download/v2.63.2/gh_2.63.2_windows_amd64.zip`
   → 解压到 `%TEMP%\gh_cli`，可执行文件 `%TEMP%\gh_cli\bin\gh.exe`。
2. **所有 `gh` / `git` 命令前先设代理环境变量**：
   `$env:HTTP_PROXY="http://127.0.0.1:3067"; $env:HTTPS_PROXY="http://127.0.0.1:3067"`
3. **自己走 OAuth 设备流，不用 `gh auth login --web`**（`gh` 的公开 client_id 是
   `178c6fc778ccc68e1d6a`）：

```powershell
$clientId = "178c6fc778ccc68e1d6a"
$resp = Invoke-RestMethod -Uri "https://github.com/login/device/code" -Method Post `
  -Body @{ client_id = $clientId; scope = "repo,read:org,workflow" } `
  -Headers @{ Accept = "application/json" } -TimeoutSec 40
# 把 user_code 交给用户在 https://github.com/login/device 输入
# 然后轮询 /login/oauth/access_token：
#   grant_type = "urn:ietf:params:oauth:grant-type:device_code"
#   error=authorization_pending -> 等 interval 秒重试
#   error=slow_down            -> 等 interval*2 秒重试
$tok | & "$env:TEMP\gh_cli\bin\gh.exe" auth login --hostname github.com --git-protocol https --with-token
```

4. 拿到登录态之后：`gh repo create QuickDrawer --public` → `git remote add origin` →
   `git push -u origin main` → `gh release create v1.0.0 ... --notes-file`。

### 验收（全部实测，不是「命令没报错」）

| 项 | 证据 |
| --- | --- |
| 登录态 | `gh auth status` → `✓ Logged in to github.com account zhhcdf (keyring)`，scopes `read:org, repo, workflow` |
| 远端文件数 | `gh api repos/zhhcdf/QuickDrawer/git/trees/main?recursive=1` → 174 个 blob，与本地 `git ls-files` 的 174 一致 |
| 提交一致 | 本地 `git rev-parse HEAD` 与 `gh api .../commits/main --jq .sha` 都是 `d3ad573ce1b6b55340f6ffae8321ce88a3d5bdb8` |
| Release 状态 | tag `v1.0.0`，`draft=false`、`prerelease=false` |
| 附件 | `QuickDrawer-1.0.0-win-x64.zip` 1,125,974 B、`SHA256SUMS.txt` 97 B，均 `state=uploaded`，大小与本地一致 |
| **端到端** | 从公开 URL `releases/download/v1.0.0/QuickDrawer-1.0.0-win-x64.zip` **匿名下载**，SHA256 = `48ce146dc77498215e75d2d01c9753cee121b9d49cdd037ee64271f0ecc69672`，与本地文件、与 `SHA256SUMS.txt` 三方一致 |
| 压缩包内容 | 19 个条目（18 个文件 + 1 个目录条目），解包总字节 2,958,155，与发布目录一致 |

### 防复发

1. **`gh` / `git` 在开着系统代理的 Windows 上必须显式设 `HTTPS_PROXY`**。
   别用「浏览器能打开 GitHub」来推断命令行工具也能连——它们读的配置源不一样。
2. **SSH 报 `Permission denied (publickey)` 不等于公钥没加**。
   先看 `-vvv` 里有没有 `Server accepts key`：有就说明服务端认公钥、问题在签名环节；
   没有才是公钥/密钥的问题。这条区分能把排查方向一次砍掉一半。
3. **`gh auth login --web` 需要真 TTY**。在非交互环境里它会打印完设备码就退出，
   而且**不留下任何配置目录**，看起来像「什么都没发生」。
   要么用 `--with-token` 从管道喂 token，要么自己实现设备流。
4. **`winget install` 挂住先看 `msiexec` 进程**。它可能在等一个不会出现的 UAC 弹窗。
   免安装的 zip 版通常更快也更可靠。
5. **PowerShell 没有 `<<<` herestring 重定向**。要把字符串喂给命令的 stdin，
   用管道 `$tok | & gh ... --with-token`。
6. **推送成功之后仍要做端到端验证**。`git push` 退出码 0 只说明对象传上去了；
   真正要确认的是「别人从 Release 页面能不能下到一个和本地逐字节相同的文件」，
   所以从公开 URL 匿名下载一次并比 SHA256。

## 一键发布脚本 `probe/_release.ps1`（2026-11-07）

### 为什么要有它

1.0.0 是手工一步步发的，九步里有四个地方容易错，而且错法都很隐蔽：

- 版本号要同步改三处（csproj 的 `<Version>` / `<AssemblyVersion>` / `<FileVersion>`、README 的 `**版本**`、
  CHANGELOG 的小节标题），漏一处发出去的版本号就是错的；
- `dotnet publish` 前必须停实例，否则 `MSB3027/MSB3021` 锁文件，而接了 `| tail` 时退出码仍是 0；
- `git push` 退出码 0 不代表发布成功，得从公开 URL 匿名下载一次比 SHA256；
- 系统代理关掉之后还硬设 `HTTPS_PROXY`，`gh` 反而报 `connectex: target machine actively refused`。

脚本把这些固定成九个带前置校验的步骤，任何一步的前提不满足就直接失败退出，不会半途留下坏状态。

### 用法

```powershell
# 先空跑看计划，不改任何东西
.\probe\_release.ps1 -Version 1.0.1 -DryRun

# 真正发布
.\probe\_release.ps1 -Version 1.0.1
```

可选参数：`-NoPush`（只做本地构建与打包）、`-Launch $false`（发完不启动）、
`-PublishDir` / `-GhExe` / `-Repo`（换环境时覆盖默认值）。

### 九步与每步的守卫

| 步 | 做什么 | 失败条件 |
| --- | --- | --- |
| 1 | 前置校验 | 版本号不是三段式 / 不在 main / 工作区有未提交改动 / 发布目录在工作区内 / dotnet 或 git 缺失 / gh 未登录 / `v<版本>` 的 Release 或 tag 已存在 |
| 2 | 从 `CHANGELOG.md` 取发布说明 | 没有 `## [版本]` 小节，或小节短于 40 字符（防占位） |
| 3 | 改三处版本号 | 任一正则匹配不到唯一一处（`<Version>` / `**版本**` / `## [x.y.z] — YYYY-MM-DD`） |
| 4 | `dotnet build -c Release` | 退出码非 0 或输出含 `error` |
| 5 | 停实例并轮询归零 | 40×250ms 后进程仍在 |
| 6 | `dotnet publish -f net48` | 退出码非 0 / 找不到 exe / **`FileVersion` 不等于 `<版本>.0`** |
| 7 | 打包 zip + `SHA256SUMS.txt` | —— |
| 8 | 提交 + 推送 | 远端 HEAD 与本地 `rev-parse HEAD` 不一致 |
| 9 | `gh release create` + 匿名下载比 SHA256 | 下载失败 / 哈希不一致 / 附件数不是 2 |

第 6 步的 `FileVersion` 校验是关键：它证明版本号真的进了二进制，而不是只改了源码没重建。

### 写脚本时踩到的坑

1. **`Write` 工具写出的 `.ps1` 没有 BOM，`powershell -File` 会把中文按 GBK 读**，
   于是 `$Version.0` 被解析成 `Missing property name after reference operator`、
   中文字符串里的句号变成 `"` 导致 `The string is missing the terminator`。
   用 `[System.Management.Automation.Language.Parser]::ParseFile` 解析时是好的
   （那里按 UTF-8 读），用 `-File` 执行才暴露 —— **两个入口的编码行为不一样**。
   修法：写完后补 UTF-8 BOM。仓库里已有的 `probe/*.ps1` 都有 BOM，只有新写的会漏。

2. **`Die()` 用的是 `exit 1`，不能被 `try/catch` 捕获。** 想验证负向用例
   （比如"CHANGELOG 里没有这一节"），必须在**独立进程**里跑，
   或者像本轮那样把函数定义抽出来用 `Invoke-Expression` 单独加载。

3. **`Resolve-Proxy` 要先探测端口是否在监听再注入环境变量。**
   代理关掉之后 `ProxyEnable` 可能还是 1（注册表没清），
   这时硬设 `HTTPS_PROXY` 会让 `gh` 报 `proxyconnect tcp: dial tcp 127.0.0.1:3067: connectex:
   No connection could be made because the target machine actively refused it`，
   比直连失败更难懂。

### 验收（都是实跑，不是"看着对"）

- `Parser::ParseFile` → `PARSE OK (tokens=2876)`；补 BOM 后 `powershell -File ... -DryRun` 能正常输出中文。
- DryRun 对 `1.0.0` 正确报 `Release v1.0.0 已存在，不能重复发布`（说明守卫有效）。
- 用 `1.0.0` 跑 `Update-VersionFiles`，三个文件 **SHA256 前后完全相同**
  （`ALL_SAME = True`），换行 CRLF/bare-LF 计数与 BOM 状态都不变 —— 证明正则与编码往返无损。
- 抽函数跑 构建→停实例→发布→打包：`0 个警告 / 0 个错误`、停掉旧 PID 7660、
  发布 18 文件 / 2,958,379 字节、`FileVersion = 1.0.0.0`、
  zip 18 条目且 `QuickDrawer.exe` 351,744 字节、`SHA256SUMS` 是 `[0-9A-F]{64}` + 双空格。

### 一个观测到的差异（不是缺陷，但要知道）

在有 git 历史之后重新构建，`ProductVersion` 会变成 `1.0.0+1403149732e4ae502e0fd67ff5a9c1e7fe1e987b`
（SDK 默认把源提交哈希拼进 InformationalVersion）。
1.0.0 那个 zip 里的 exe 是 `ProductVersion = 1.0.0`（那时还没 `git init`）。
`FileVersion` 始终是干净的 `1.0.0.0`，资源管理器里显示的是它，所以对外观感没影响。
如果希望 `ProductVersion` 也干净，在 csproj 里加
`<IncludeSourceRevisionInInformationalVersion>false</IncludeSourceRevisionInInformationalVersion>`。
本轮没有改，因为调试时能从版本号直接看出是哪个提交构建的，反而有用。

- 改 `C:\Windows\System32\drivers\etc\hosts` 把名字指到可用 IP → `Access to the path ... is denied`，需要管理员权限。
- `git -c http.curloptResolve=github.com:443:140.82.112.3 ...` → **git 2.21.0 不认识这个配置项**，行为不变，照样超时。

### 绕行：用 `gh api` 的 contents 接口提交，只走 `api.github.com`

```powershell
$b64 = [Convert]::ToBase64String([System.IO.File]::ReadAllBytes("README.md"))
$payload = @{
  message = "README：删掉体积说明、路线取舍、裁剪不可行、net48 迁移踩坑等实现细节"
  content = $b64
  sha     = "70f258112b7f7f4a75ce7cba74e7672a243b5bbc"   # 远端当前 blob
  branch  = "main"
} | ConvertTo-Json -Compress
$payload | Set-Content payload.json -Encoding utf8
& "D:\software\gh\gh.exe" api --method PUT repos/zhhcdf/QuickDrawer/contents/README.md --input payload.json
```

返回新 commit `203f9aeb57571bdbe8e253002e72f57711c0b7be`，`content.size = 10181`。

### 两棵树对齐（关键，否则下次 push 会分叉）

API 提交产生的 commit SHA 与本地 `git commit` 产生的不同（前者是 GitHub 服务端算的），但**内容 tree 完全相同**（`52fee7e0...`）。

要把本地指到同一个 commit，不能 `git fetch`（同样走 github.com，超时），只能**在本地重建出字节完全一致的 commit 对象**：

```python
# 关键：时区必须是 +0800。API 返回的是 2026-11-07T09:15:06Z，
# 换算成本地时间后写成 +0800，git 才能算出同一个 SHA。
commit = "tree 52fee7e0...
"          "parent edbcb83...
"          "author zhhcdf <zhouhongc@gmail.com> 1762504506 +0800
"          "committer zhhcdf <zhouhongc@gmail.com> 1762504506 +0800
"          "
"          "README：删掉体积说明、路线取舍、裁剪不可行、net48 迁移踩坑等实现细节
"
```

```powershell
$c = "..." | & git hash-object -t commit -w --stdin
git update-ref refs/heads/main $c
git reset --hard $c
```

对齐后：本地 `HEAD` = 远端 `HEAD` = `203f9ae...`，`git status` 干净，远端 README 与本地**逐字节相同**（10,181 字节，`IDENTICAL: True`）。

### 验收

| 项 | 结果 |
| --- | --- |
| 本地 HEAD | `203f9aeb57571bdbe8e253002e72f57711c0b7be` |
| 远端 `commits/main` | `203f9aeb57571bdbe8e253002e72f57711c0b7be` |
| 本地 worktree | `git status --porcelain` 空 |
| 远端 README 大小 | 10,181 字节，blob `a33962a581d72e43ab52cae291a176a0b87e2d36` |
| 远端 README 残留关键词 | `体积说明/2.82/65.39/PublishTrimmed/NETSDK1168/单文件/裁剪` 全 0 |
| 远端 README 行数 | 188 |
| Release v1.0.0 说明残留 | `2.82/MB/体积/65.39/裁剪/net48` 全 0 |

### 防复发

1. **`git push` 失败先分清"整站不通"还是"某个 IP 不通"** —— 分别测 `github.com:443`、`api.github.com:443`、以及同一域名的其它 IP。这里就是单 IP 问题，误判成"被墙"会白等。
2. **`api.github.com` 可用时，`gh api` 的 contents / git trees / git refs 接口可以完整替代 push** —— 但每次都会产生服务端 commit，本地必须对齐。
3. **对齐 commit 时区必须写 `+0800`（本地时区）**，用 `Z` 或别的偏移算出的 SHA 一定不同，会白跑一轮。
4. **`git 2.21.0` 没有 `http.curloptResolve`**，不要指望用配置项绕 DNS；`hosts` 需要管理员，也不要把它当可用方案。
5. **改 README 的同时要想远端 Release 说明** —— 两者都是"面向使用者"的文案，用户说"应用说明"时指的是这两处，改完要各自复核一遍残留关键词。
6. **删"为什么这么设计"类内容时，区分"历史"和"仍在生效的约束"** —— `PlatformTarget=x64` 这类删了会让人重踩，必须留。

## 富格式写回不写纯文本：除 Word 外全都粘不出来（2026-11-07 晚）

### 现象

用户报告：

> 我发现在 obsidian 里复制的内容，再次从剪贴板历史里复制非常困难，只有在 word 文档里粘贴可行，在其他地方粘贴都不成功。

即：在 QuickDrawer 面板里点历史里的 HTML 条目（来源是 Obsidian），面板把内容写回剪贴板并注入 Ctrl+V，
Word 能粘出内容，记事本 / 浏览器输入框 / 聊天框 / 终端 / 其他编辑器全部粘出空白。

### 根因

**写回 HTML / RTF 条目时只往剪贴板放了富格式，没有放纯文本。**

`ClipboardService.WriteBack` 的 Html 分支原本是：

```csharp
case ClipKind.Html:
    if (WriteHtmlPayload(entry.Text ?? "", entry.HtmlStyle)) return true;
    return WriteTextPayload(entry.Preview ?? "");   // 只有 HTML 写失败才走这里
```

Rtf 分支同样只 `SetClipboardData(rtfId)`。于是在**成功路径**上，剪贴板里只有一个格式：

- HTML 条目 → 只有 `HTML Format`（注册格式 49409）
- RTF 条目 → 只有 `Rich Text Format`（49307）

Windows 剪贴板是"一种数据、多种并列格式"的模型，各程序按自己认识的格式去取：
Word / WordPad 认识 `HTML Format`，所以能粘；记事本、浏览器地址栏与输入框、
QQ / 微信 / 钉钉聊天框、终端、`EDIT` 控件这些**只读 `CF_UNICODETEXT`（格式 13）**，
拿不到就静默粘出空。

现场实测（对用户剪贴板直接枚举格式）：

```
仅 fmt 49409 'HTML Format' size=188
载荷：Version:0.9\r\nStartHTML:0000000107\r\n...<!--StartFragment--><!-- obsidian --><p>「发送」按钮</p><!--EndFragment-->
```

`StartHTML == 107` 正是 `WriteHtmlPayload` 里 `HEAD_FMT` 求出的 `headLen`，确认是自己写出去的。
`diag.log` 同一时段**没有** `write back failed`，说明 `WriteBack` 返回成功 —— 不是写失败，是写得太少。

**为什么捕获侧也留不住纯文本**：`TryReadClipboard` 按 文件 > HTML > RTF > 文本 > 图片 单选返回，
HTML 命中就立即 return，源程序同时放在剪贴板上的 `CF_UNICODETEXT` 被整个丢弃，
`ClipEntry` 里也没有任何字段能存它。所以即使写回时想补纯文本，也**没有原料**。

HTML 必须排在文本前面这条不能动：否则从 Word / Excel 复制的表格会退化成制表符拼接的文本，
表格结构就没了（这是既有设计，注释里写明了原因）。

### 修复

思路：**富格式和纯文本是并列格式，不是替代关系。** 捕获时把源程序的纯文本留一份，
写回时两种格式一起放。`Selection/SelectionCapture.cs` 的 `RestoreClipboard` 本来就是同时写
Text + Html + Rtf，说明多格式并存是本项目既有做法，不算引入新的复杂度。

`src/QuickDrawer/ClipboardService.cs`：

1. `ClipEntry` 新增 `public string? PlainText { get; set; }`（紧跟 `HtmlStyle`）。
2. 抽出 `private static string? ReadPlainTextFromClipboard()`（原 `ReadText` 的取数逻辑），
   `CF_UNICODETEXT → CF_TEXT → CF_OEMTEXT` 三级兜底，只返回字符串不构造条目。
3. `ReadHtml()`：优先取源程序的 `CF_UNICODETEXT`，拿不到才用 `HtmlToPlainText(fragment)` 反推；
   `SizeBytes` 把纯文本也算进去，避免体积统计漏算。
4. `ReadRtf()`：同上，拿不到才 `StripRtf(s)`。
5. 新增 `private static string HtmlToPlainText(string html)`：逐字符扫描，跳过 `<!-- ... -->`
   整段（Obsidian 会写 `<!-- obsidian -->`），`<br>` 与块级闭合标签 → 换行，`<td>/<th>` → 制表符，
   其余标签丢弃，`WebUtility.HtmlDecode` 反转义，按行 Trim 并压掉连续空行。
6. `WriteBack` 的 Html / Rtf 分支：先把纯文本写进 `CF_UNICODETEXT`，再写富格式；
   富格式失败也不再算整体失败（内容还在，只是丢样式）。
7. `WriteBack` 的 Text 分支顺手改为 `return WriteTextPayload(entry.Text ?? "");`
   —— 原来内联复制了一份 `GlobalAlloc` + `Marshal.Copy`，和 `WriteTextPayload` 是重复代码。

`src/QuickDrawer/ClipboardStore.cs` 五处（`SecretPayload` / `ClipSnapshot` 构造 / `SnapshotAll` /
`SaveSnapshot` / `Load`）同步加 `PlainText`，沿用 `htmlStyle` 的"末位可选参数"写法，旧文件读进来是 `null`。

**旧历史条目（`PlainText == null`）怎么办**：写回时现场从 `entry.Text` 反推
（`HtmlToPlainText` / `StripRtf`），所以升级后不需要重建历史也能正常粘贴。

### 排查过程中一并修掉的三个真实缺陷

1. **`HtmlToPlainText` 末尾多一个换行** —— `</p>` 产生的 `\n` 没被 `TrimEnd` 掉，
   从旧条目粘到记事本会平白多一个空行。改为 `TrimEnd('\n')`。
2. **`HtmlToPlainText` 输出裸 `\n`** —— Windows 剪贴板 `CF_UNICODETEXT` 的换行惯例是 `\r\n`。
   记事本看着没错，但 `EDIT` 单行控件、部分终端、逐字符处理的脚本会把 `\n` 当普通空白。
   改为 `TrimEnd('\n').Replace("\n", "\r\n")`（内部仍用 `\n` 拼，只在出口转，注释写明原因）。
3. **`StripRtf` 的 `\ucN` 回退字符漏跳普通字符形式** —— 原实现只跳 `\'hh` 这种十六进制写法，
   Word 写的 `\u20013?` 里那个 `?` 是**回退占位符**不是正文，却被当成文本输出，
   粘出来是「中?」。改为：先判 `\'hh` 走 4 字符，遇到 `\\` / `{` / `}` 就 break（后面是控制字不是回退），
   否则逐字符跳过。

### 验证方法

三个门禁，全部 PASS：

| 探针 | 判据 | 结果 |
| --- | --- | --- |
| `probe/clip-formats` | 直接调 `WriteBack`，枚举剪贴板格式，断言每个用例都有 `CF_UNICODETEXT` 且**全文精确匹配**、富格式仍在 | PASS，5 个用例全绿 |
| `probe/clip-e2e` | 建真实 Win32 窗口 + `EDIT` 控件（记事本同款），`WM_PASTE` 后 `WM_GETTEXT` 读回；覆盖 Obsidian 真实载荷形状 + DPAPI 存取 + 旧条目回退 | PASS |
| `probe/_verify_writeback.ps1` | PowerShell 宿主，8 项断言 | PASS |

关键实测数据：

- 修复前 `clip-e2e` 第 1 段：剪贴板只有 `HTML Format` 时，`EDIT` 粘出 `''`（0 字符）—— bug 在真实控件上复现。
- 修复后第 4 段：格式为 `UnicodeText / HTML Format / Locale / Text / OEMText`，
  `EDIT` 粘出 29 字符**精确匹配**，`html still on clipboard: True` —— 纯文本目标与富格式目标同时满足。
- 第 2 段：捕获到的 `PlainText` 与源程序放在剪贴板上的 `CF_UNICODETEXT` **逐字符相等**
  （`&amp;` 已正确解码为 `&`，`<!-- obsidian -->` 没泄漏），说明是"直接取原文"而不是"反推"。
- 第 5 段（旧条目、`PlainText == null`）：派生出 `旧条目\r\nsecond line`，`uses CRLF: True`、`has bare LF: False`。
- `clip-formats` E 例：900 字输入 → `fmt 13 size=1802`，证明写的是**全文**而不是 200 字 `Preview`。

### 防复发

1. **`probe/_verify_writeback.ps1` 原来只校验 CF_HTML 四个偏移** —— 正是这个盲区让 bug 发出去还没被发现。
   现在加了 4 项：`CF_UNICODETEXT present`（缺失时打印 `MISSING - only Word could paste this`）、
   `plain text is not the preview`、`plain text has no markup`、`derived text is TAB/CRLF joined`。
   对**旧发布版** exe 跑会 FAIL，对新版跑 PASS —— 已实测门禁有效。
2. **PowerShell 里给 `string?` 属性赋 `$null` 会落成 `""`**，于是 `x ?? fallback` 不触发。
   凡是"可选字符串 + 回退"的地方一律用 `string.IsNullOrEmpty`，不要用 `??`。
   这个坑曾让 `_verify_writeback.ps1` 在新旧两个 exe 上都报 FAIL，白查了一轮。
3. **`probe/*.ps1` 含中文时必须存成 UTF-8 with BOM**，否则 Windows PowerShell 5.1 按 ANSI 读，
   会在中文注释处字节错位并报 `Unexpected token '}'`。`_verify_writeback.ps1` 已修成 BOM；
   其余脚本（`_verify_word_table.ps1`、`_verify_excel_pasteback.ps1`、`_verify_selection_rich.ps1` 等）仍是
   `bom=False nonAscii=True`，下次在 5.1 下跑之前先转 BOM。
4. **探针抢不到剪贴板（`0x800401D0 CLIPBRD_E_CANT_OPEN`）时要重试**，不能当产品失败也不会崩。
   `clip-verify` 的 `SetTextRetry` 从 20 次 ×100ms 提到 60 次 ×6s，并在失败时打印
   `GetOpenClipboardWindow` + PID + 进程名，超时抛带占用者信息的异常。
   实测同样代码曾"一次 PASS 一次崩溃"，属偶发占用而非缺陷。
5. **剪贴板相关的修复必须以"真实控件粘得出来"为验收** —— 枚举格式只能证明"写了"，
   不能证明"别的程序认得"。`clip-e2e` 用 `EDIT` 控件 `WM_PASTE` 是本项目此后这类问题的标准判据。

## 全屏游戏/视频误触拉手：自动隐藏 + 副产品 MonitorFromPoint 既有 bug（2026-11-08）

### 现象

> 为了避免在全屏游戏等情况下误触拉手，影响游戏体验。我想在全屏游戏时能临时关闭拉手热区。
> —— 用户原话，2026-11-08

拉手（`HandleWindow`）贴屏幕右边缘垂直居中，`Handle_MouseEnter` 一进来就 `Expand()` 并 `HoverRequested`
立刻弹面板。全屏游戏时鼠标移到屏幕右侧边缘（切枪、转视角、拖滚动条）就会撞上它，面板盖在游戏画面上。

用户补充要求：全屏视频也要隐藏；用托盘菜单手动开关，**不要**"暂停 N 分钟"那种定时配置；
并问"退出全屏后如何激活拉手"。

### 根因

不是 bug，是**从未实现的功能**：拉手只在 `DrawerWindow` 的 `Loaded` 里创建一次，
此后没有任何"该不该显示"的判定，`Visibility` 只由面板开合驱动。

摸底时还确认了两个坑：

1. `src/QuickDrawer/Config.cs:132-134` 的 `DockConfig.HotZonePx` **全项目零引用** ——
   一个从未接线的空配置项。想用它做"热区大小"的开关是不行的。
2. 现有投影逻辑 `AdjustForTaskbar` / `WindowPushOut` 里有 `fillsMonitor && !IsZoomed` 的反筛
   （`src/QuickDrawer/WindowPushOut.cs:206-212`），但那是**拿 rcWork 比**，用来判断"要不要推窗口"；
   本需求要判断"是不是真全屏"，基准不同（见下）。

### 判定信号的取舍（这段是本次的核心决策）

| 信号 | 覆盖 | 为什么用 / 不用 |
| --- | --- | --- |
| 前台窗口矩形 == 光标所在显示器 `rcMonitor` | 无边框全屏、F11、大部分游戏 | **主判据**。用 `rcMonitor`（含任务栏区域）而不是 `rcWork`：无边框全屏与"最大化"的真正分野就是任务栏那 48px，比 rcWork 少一层 `IsZoomed` 判断 |
| `DwmGetWindowAttribute(DWMWA_CLOAKED)` | 排除 UWP 幽灵窗口 | 幽灵窗口几何上也是整屏，但人看不见它，不该据此隐藏拉手 |
| 排除本进程 pid | 防自锁 | 否则 QuickDrawer 自己的面板被判定成全屏，拉手永远藏起来 |
| `SHQueryUserNotificationState == QUNS_RUNNING_D3D_FULL_SCREEN(3)` | 独占全屏（DirectX 游戏） | 独占全屏时前台窗口矩形常常拿不准，靠这个补 |
| `EVENT_SYSTEM_FOREGROUND` 前台钩子 | 不做 | F11 全屏是在**同一个窗口**上改矩形，前台句柄不变，钩子根本不触发。轮询 500ms 天然覆盖这种情形，且每 tick 只有三个廉价系统调用 |
| 多显示器按**光标所在屏**判定 | 多屏 | 因为 `HandleWindow.PositionHandle()` 用 `GetWorkAreaForCursor()` 定位，拉手贴的是光标那块屏。按前台窗口所在屏判定会在"游戏在全屏 A、鼠标在 B"时误藏 |

### 实现

**① `src/QuickDrawer/Native/Native.cs`** 新增「全屏检测」段（`ClassNameOf` 之后）：

- `public static bool TryGetMonitorRect(IntPtr hMonitor, out Rect monitor)` —— 取 `MONITORINFO.rcMonitor`。
- `public static IntPtr GetMonitorForCursor()` —— `GetCursorPos` → `MonitorFromPoint(p, MONITOR_DEFAULTTONEAREST)`。
- `public static bool IsForegroundFullscreenOnCursorMonitor(out IntPtr hwnd, out string reason)` ——
  依次过：前台非零 → 排除本进程 → `IsWindowVisible` → 非 cloaked → 取光标屏 rcMonitor → `GetWindowRect`
  → 四边 `Math.Abs(diff) <= 2`。**每条失败路径都填 `reason` 字符串**（`"own process"` / `"cloaked"` /
  `"rect {l},{t}-{r},{b} vs monitor ..."` / `"fills {l},{t}-{r},{b}"`），诊断日志据此可判断是"没全屏"还是"检测坏了"。
- `public static bool IsD3DFullscreen()` —— `SHQueryUserNotificationState(out int state)` 的 `hr == 0 && state == 3`。

**② `src/QuickDrawer/Config.cs`** `HandleConfig` 末尾：

```csharp
[JsonPropertyName("hideInFullscreen")]
public bool HideInFullscreen { get; set; } = true;
```

**③ `src/QuickDrawer/DrawerWindow.xaml.cs`** 新增三个字段 + 一个 500ms 定时器：

```csharp
private System.Windows.Threading.DispatcherTimer? _fullscreenTimer;
private bool _handleSuppressedByFullscreen;
private bool _handleVisible;
```

`StartFullscreenWatch()` / `StopFullscreenWatch()` / `FullscreenTimer_Tick(...)` /
**`UpdateHandleVisibility()`**。后者是拉手可见性的**唯一判定点**：

```csharp
bool shouldShow = !_isOpen && !_handleSuppressedByFullscreen;
if (shouldShow == _handleVisible) return;
_handleVisible = shouldShow;
if (shouldShow) _handle.ShowForPanel(); else _handle.HideForPanel();
```

原来 `ShowAnimated` 里直调 `_handle?.HideForPanel()`、`HideAnimated` 动画完成时直调
`_handle?.ShowForPanel()` 的两处**必须收口**改成 `UpdateHandleVisibility()`，否则 `_handleVisible`
与真实可见性脱节：全屏中收起面板会无条件把拉手弹到游戏画面上。

`Tick` 里只在**状态翻转**时动作（`fullscreen != _handleSuppressedByFullscreen`），
进入写 `hidden: fullscreen detected hwnd=0x.. class=.. {reason}`，退出写 `restored: no longer fullscreen`。

**④ 托盘菜单**（`OpenAppMenu`，「设置…」之后）：

```csharp
var hideFullscreen = new MenuItem {
    Header = "全屏时隐藏拉手", IsCheckable = true,
    IsChecked = _config.Dock.Handle.HideInFullscreen,
    IsEnabled = _handle is not null
};
hideFullscreen.Click += (_, _) => {
    bool target = !_config.Dock.Handle.HideInFullscreen;
    _config.Dock.Handle.HideInFullscreen = target;
    ConfigStore.Save(_config);
    hideFullscreen.IsChecked = target;
    if (!target) { _handleSuppressedByFullscreen = false; }   // 必须清，否则照样不显示
    DiagLog.Write("handle", $"tray toggle: hideInFullscreen={target}");
    UpdateHandleVisibility();                                  // 不等下一个 tick
};
```

放托盘而不是设置页的理由：这是"当场要关"的动作，进了全屏游戏就点不到设置页；
而且它同时是**检测失效时的唯一逃生门** —— 拉手已被藏起来，没法从拉手上唤起面板。

### 副产品：`MonitorFromPoint` 的 P/Invoke 一直是错的（既有 bug）

写门禁探针时第 2/3/4 段全报 `reason=no monitor rect`，即 `GetMonitorForCursor()` 返回 `IntPtr.Zero`。

用 `probe/_diag_fs3.ps1` 做同进程对照（`EntryPoint="MonitorFromPoint"` 声明两个形状）：

```
MonitorFromPoint(POINT pt, uint flags)      -> 0x10001   GetMonitorInfo=True   rcMonitor=0,0-1920,1080
MonitorFromPoint(int x, int y, uint flags)  -> 0x0       GetMonitorInfo=False
```

**根因**：Win32 原型是 `MonitorFromPoint(POINT pt, DWORD dwFlags)`，`POINT` 是 8 字节结构体按值传递。
x86 上拆成两个 `int` 参数堆栈布局恰好等价，所以看不出来；本项目 `PlatformTarget=x64`，
x64 下 `POINT` 只占**一个**寄存器，拆开后 `dwFlags` 被顶到第三个参数槽，user32 拿到垃圾 flags → 直接返回 NULL。

**影响面比这次的需求更大**：`GetWorkAreaForCursor()` 一直走进 `SystemParametersWorkArea()` 兜底 ——
返回的是**主屏工作区的 DIP 坐标**，不是光标所在显示器的**物理像素**。单显示器 + 100% 缩放下两者恰好相同，
所以从 2026-11-01 到现在没人发现。9 个调用点受影响：
`src/QuickDrawer/DrawerWindow.xaml.cs:270,373,448,543,552,2633`、
`src/QuickDrawer/HandleWindow.xaml.cs:67,109,142,201`、
`src/QuickDrawer/Selection/SelectionPopup.cs:251`。
**多显示器或高 DPI 下，拉手 / 面板 / 选区弹窗过去一直贴错屏。** 这次一并修好了。

### 验证方法

`probe/_verify_fullscreen_handle.ps1`（纯 ASCII，无需 BOM；`$env:QD_EXE` 指定 exe）。四段：

1. 反射检查 API 面（16 项）：4 个 `NativeMethods` 方法、`HandleConfig.HideInFullscreen`
   （默认 true、JSON 名 `hideInFullscreen`）、`HandleWindow.HideForPanel/ShowForPanel`、
   `DrawerWindow` 的 4 个方法 + 3 个字段。
2. 正常桌面下**必须**判"非全屏" —— 防误报，否则拉手平时就没了。
3. **另起 powershell 子进程**建一个无边框 TopMost 全屏 `Form` ——
   必须跨进程，因为判定会排除本进程窗口，同进程建窗口永远测不出全屏。
   把光标移到该窗口中心、`SetForegroundWindow` 直到前台确实是它，再断言"判为全屏且 hwnd 就是子窗口"。
4. 杀掉子进程后断言**翻回"非全屏"** —— 验证"退出全屏自动恢复"这条链路。

实测结果（2026-11-08）：

```
PASS  foreground is not fullscreen  reason=rect 286,123-1690,951 vs monitor 0,0-1920,1080
PASS  IsD3DFullscreen() callable  returned=False
PASS  child window is foreground  foreground=0x607FA child=0x607FA
PASS  fullscreen detected  reason=fills 0,0-1920,1080
PASS  culprit hwnd is the child  reported=0x607FA
PASS  back to not-fullscreen  reason=rect 286,123-1690,951 vs monitor 0,0-1920,1080
RESULT: PASS
```

### 失败模式与逃生

| 情形 | 表现 | 怎么救 |
| --- | --- | --- |
| 游戏崩溃 / 正常退出 | 前台变了，下一个 tick 翻假，拉手自动回来 | 无需操作 |
| 游戏假死但占着前台 | 一直判为全屏，拉手一直藏着 | 托盘菜单取消勾选「全屏时隐藏拉手」→ 立刻 `UpdateHandleVisibility()` 显示回来 |
| 检测漏判（不认作全屏） | 拉手露出，可能仍误触 | 无损害，退回改动前的行为 |
| 检测误判（桌面也认成全屏） | 拉手平时就不见了 | 同上，托盘菜单取消勾选 |

### 防复发

1. **P/Invoke 结构体参数不能拆**。`POINT` / `RECT` / `SIZE` 这类小结构体按值传参时，
   必须声明成结构体，不能图省事拆成两个 `int`。x86 上"碰巧能跑"是最坏的坑 ——
   迁移到 x64 才炸，而且炸得静默（返回 NULL / 零值，不是异常）。
   本仓库同类风险点：`Native.cs` 里所有带 `out POINT` / `out RECT` 的声明下次一并复核。
2. **`PlatformTarget=x64` 是在 csproj 里写死的**（否则 WebView2Loader 会挑 x86 抛
   `BadImageFormatException`）。这意味着任何"在 x86 上测试通过"的 P/Invoke 假设都不成立。
3. **可见性判定的入口只能有一个**。`UpdateHandleVisibility()` 之后再有人想直接调
   `HideForPanel()` / `ShowForPanel()`，`_handleVisible` 就会和真实状态脱节 ——
   这是"全屏中收起面板把拉手弹到游戏上"的复发路径。改动 `ShowAnimated` / `HideAnimated`
   的动画回调时尤其注意。
4. **门禁探针必须跨进程构造全屏窗口**。同进程会被"排除本进程 pid"这条规则挡掉，
   写出的探针永远看不到全屏，等于没测。
5. **诊断 reason 字符串不要省**。这次定位 `no monitor rect` 全靠每条失败路径都带了
   `reason`；如果只返回 bool，就得再写一轮探针才能分辨"没全屏"和"检测坏了"。

## C3 · 纯桌面被误判为全屏，拉手被藏（2026-11-08）

### 现象

用户在 1.0.2 实测反馈（原话）：「游戏和视频全屏测试都通过了。发现一个问题：纯桌面无窗口的时候会被识别为全屏而隐藏拉手。」

`diag.log` 里能直接看到误判，反复出现：

```
2026-11-08 14:57:06.034 [handle] hidden: fullscreen detected hwnd=0x65858 class=Progman fills 0,0-1920,1080
2026-11-08 14:57:42.551 [handle] restored: no longer fullscreen
2026-11-08 14:57:49.050 [handle] hidden: fullscreen detected hwnd=0x65858 class=Progman fills 0,0-1920,1080
```

注意 `class=Progman`、`fills 0,0-1920,1080` —— 判定逻辑本身没算错，它确实铺满了整块屏。

### 根因

点桌面或"显示桌面"之后，**前台窗口会变成资源管理器用来铺壁纸的那层 shell 窗口**
（`Progman`，或 `WorkerW`；Win10/11 上按桌面是否开"幻灯片壁纸"/是否装了壁纸引擎而不同层）。
这类窗口天生就铺满整个 `rcMonitor`，所以 `IsForegroundFullscreenOnCursorMonitor` 的几何判定
必然命中 —— 但它显然不是"全屏应用"，用户这时恰恰最需要拉手。

这是"几何判定全屏"这条思路的固有盲区：**它只回答"有没有东西铺满屏"，不回答"这算不算应用"。**

### 验证方法

`probe/_repro_desktop_fullscreen.ps1`（新增）：

1. 记录当前判定结果；
2. `Shell.Application.ToggleDesktop()` 切到桌面，等 1.2s；
3. 再判一次 —— 修复前输出：

```
[desktop shown]
  foreground = 0x1807A2  class=WorkerW
  fullscreen verdict = True   reason = fills 0,0-1920,1080
RESULT: REPRODUCED - bare desktop is misdetected as fullscreen
```

修复后同一脚本输出 `fullscreen verdict = False   reason = shell desktop (WorkerW)`，脚本打 `RESULT: OK`。

### 修复

`src/QuickDrawer/Native/Native.cs`：

1. 新增 `public static bool IsShellDesktopWindow(IntPtr hwnd)`：按类名排除
   `Progman` / `WorkerW` / `SHELLDLL_DefView` / `Shell_TrayWnd` / `Shell_SecondaryTrayWnd`，
   再兜底比 `GetDesktopWindow()`、`GetShellWindow()` 两个句柄。
2. `IsForegroundFullscreenOnCursorMonitor` 在 `IsWindowVisible` 检查之后、几何判定之前插入这道闸，
   命中时 `reason = $"shell desktop ({ClassNameOf(hwnd)})"`。
3. 新增 `GetShellWindow` / `GetDesktopWindow` 两个 P/Invoke 声明。

放在几何判定**之前**而不是之后：既省一次 `GetWindowRect`，也让日志直接说明是"桌面"而不是
"矩形不匹配"，下次看日志不用再推理一遍。

### 门禁补强

`probe/_verify_fullscreen_handle.ps1` 新增第 2b 段「bare desktop: must NOT look fullscreen」，
用 `Shell.Application.ToggleDesktop()` 切桌面 → 断言判定为 false → `finally` 里切回来。
这一段就是本次回归的漏检点：原探针只测了「普通窗口不算全屏」和「真全屏窗口算全屏」，
没测「桌面这种天然铺满屏的非应用窗口」。

### 防复发

1. **"铺满屏"不等于"全屏应用"**。任何基于矩形面积的判定都要先问一句：shell 自己的窗口会不会也满足？
   桌面（Progman/WorkerW）、任务栏（Shell_TrayWnd）、屏幕保护这几类必须显式排除。
2. 排除要**用工具体类型/类名**，不要靠"窗口标题为空"这类间接特征 —— 很多无标题应用窗口会误伤。
3. 门禁探针要覆盖「非应用窗口」这一类，只测真应用（普通窗 + 全屏窗）是不够的。
4. 桌面窗口有多层（Progman 下挂 SHELLDLL_DefView，再下是 WorkerW），不同 Windows 版本/壁纸设置
   下前台命中的是哪一层不一样，所以排除表要列全，不能只写 `Progman`。

### 影响面

只影响全屏判定的排除规则，不改动其他逻辑。桌面状态下拉手恢复显示（这正是用户要的），
真全屏应用与全屏视频的隐藏行为不变 —— 第 3、4 段门禁仍 PASS 可证。
